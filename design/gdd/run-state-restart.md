> **Implements Pillar**: Pillar 2 (Fair but Merciless Difficulty: every death is the player's own and the next attempt starts at once), Pillar 1 (Instant Readability: the Hit phase holds the world still so the killer hazard stays isolated and readable), Pillar 4 (One-Thumb Simplicity: tap-anywhere restart, no gestures)

## Overview

Run State & Restart is the Core-layer state machine that says which phase of play the game is in and announces every change of phase to the systems that react to it. It owns the run lifecycle, from the menu through a run in progress, a pause and a hit to the next run, and it owns the restart: the single path by which a run ends and a new one begins, in under one second from the player's tap (art bible section 2). It holds no gameplay data of its own (score, speed and distance belong to other systems) and has no dependencies. Tube Track, Ball Movement, Obstacle System, Pattern & Difficulty, Camera, Juice & Feedback, Scoring & Personal Best, HUD, Menus & Screen Flow and Playtest Telemetry all react to its events, and it is the single source of truth for those event names. In the MVP there is one run mode on one map with no lives and no checkpoints: one hit ends the run. Players never interact with it directly; they feel it only as the moment between a hit and the next run.

## Player Fantasy

Run State & Restart is infrastructure: players never see a state machine. They feel two things it makes possible.

1. **Again, no shame.** A hit is a sharp, exact sting followed at once by "again" (art bible, mood state 5). After a short sting the player cannot skip (half a second), one tap starts the next run within a fraction of a second. The gap between dying and running again is short enough that the player's mind never leaves the run: no loading, no results screen to dismiss, no menu to navigate. This serves Pillar 2: every death traces back to the player's own choice, and the next attempt starts before that lesson fades.
2. **The run only ends when I lose.** Nothing but a hit ends a run. A phone call, a notification or a swipe to the home screen pauses the run, and it is exactly where the player left it when they return. An interruption or a long freeze pauses the run and never ends it, and a short hitch costs a moment of time, never a jump (on a clamped frame the ball moves at most `DT_MAX` x `v_max` = 2.5 u at the defaults): the player is never punished for the world outside the game. (If the OS terminates the app while it is in the background, the run is lost: the MVP does not save runs in progress, Open Question 6.)

**Feelings to avoid:** waiting between runs (a retry screen, a loading bar, a forced delay), a death that feels like a verdict rather than a sting (mocking text, shame), and losing a run to something the player did not do.

## Detailed Design

### Core Rules

1. **One phase at a time.** The game is always in exactly one phase: Boot, Menu, Running, Paused, Resuming or Hit. Run State is the only owner of the phase; no other system stores or infers it.
2. **Events out, never calls.** Run State announces changes with signals and never calls methods on other systems. Wiring an event to a system's own API (for example Tube Track's `begin_run()`) is done by a thin adapter owned by that system. Run State has no dependencies.
3. **Requests in, validated by phase.** Other systems change the phase only by sending a request (table below). A request is queued when it is sent and processed at the next tick, with one exception (below). A request that is not valid in the current phase is ignored: no state change, no event, one log line. The level is fixed by class. **Silent**: `pause_requested(app_interrupted)`, `pause_requested(back)` and `pause_requested(sensor_lost)` outside Running and Resuming. **Debug** (expected rejections): a restart or menu press inside a lock (the Hit lock or the Paused guard); a `hit_reported` with a stale `run_id`, on a settling tick, discarded by the stall guard, or in Paused, Resuming or Hit (the world is frozen or the run is over); a repeated tap (`restart_requested` in Running, `resume_requested` in Resuming, `pause_requested(button)` in Paused); and any request that was valid in the phase before an earlier request on the same tick changed it and is rejected only because of that change (a request that was already invalid before the change is classified by the phase at its turn, as usual: with a hit on the same tick, a `pause_requested(button)` sent from Running is debug and a `resume_requested` is a warning). **Warning**: every other invalid request (for instance `start_requested` in Running, `hit_reported` in Menu or Boot, `pause_requested(button)` in Hit, Menu or Boot). **Error**: a request sent from inside a Run State event handler or a tick (transitions never nest), a bad config value and a bad `press_us`. Logs go to an injected sink `log_sink(level, message)`.
   **App interruption (the one request that is not queued).** OS notifications arrive between frames, so `pause_requested(app_interrupted)` is applied at the moment it is sent, not at the next tick: in Running or Resuming it pauses at once (`run_paused(app_interrupted)`). The world is frozen from that moment, so a `hit_reported` that is still queued, or that the first frame after the player returns would have produced, meets the phase Paused and is ignored: an interruption never ends a run. Sent from inside a handler or a tick it is rejected like any other request.
   **Frame model.** Run State is driven by one `tick(world_dt, real_dt)` per frame, called by the same owner and in the same loop as Tube Track's `advance(s)` (one tick source; Tube Track Open Question 4). `tick()` returns `dt_eff`, the world step of this frame; the owner passes that same value to Ball Movement, which integrates `s` with it and hands `s` to Tube Track's `advance(s)`, so the run clock, the ball and the tube always agree. `real_dt` is computed by the owner from the injected clock (this tick's `now_us` minus the previous one), never from the engine's `delta`. Verified on Godot 4.7.2 (2026-09-20 review): `delta` is scaled by `Engine.time_scale` and is capped by the engine at about `max_physics_steps_per_frame / physics_ticks_per_second` (0.133 s at the project defaults; a 1.5 s stall gave a `_process` delta of 0.13 s), so a stall guard fed with `delta` could never reach `STALL_PAUSE_THRESHOLD`. `world_dt` may be scaled by hitstop or time scale. **Owner contract:** after `tick()` returns, the owner steps Ball Movement by the returned `dt_eff` and calls Tube Track's `advance(s)` with the resulting `s` (a 0 step may be skipped), and only when the phase now reads Running; it never calls Tube Track's `advance()` when the phase is not Running (Tube Track rejects it with an error), and Ball Movement, Obstacle System and Tube Track never read the engine's `delta` themselves. One tick, in this order, with one `now_us` snapshot taken at its start:
   1. **Stall guard.** If the phase at the start of the tick is Running or Resuming, the tick is not a settling tick and `real_dt >= STALL_PAUSE_THRESHOLD`, Run State pauses as for `app_interrupted` (`run_paused(app_interrupted)`) and discards every `hit_reported` queued on this tick. The player is never killed by a frame they could not see.
   2. **Step candidate (F1).** If the phase at the start of the tick is Running, no stall pause happened and the tick is not a settling tick, `step = min(world_dt, DT_MAX)`; otherwise `step = 0`. It is not applied yet.
   3. **Requests**, in class priority order: `hit_reported`, `pause_requested`, `resume_requested`, `menu_requested`, `restart_requested`, `map_ready`, `start_requested`; within one class in arrival order, except that all `hit_reported` of the tick are taken together: those with a stale `run_id` are dropped first (debug log), and among the rest the one with the lowest non-negative `hazard_id` wins, `-1` only if no known id is present (Edge Cases). Each request is validated against the phase as it stands after the previous one, so a hit and a pause on one frame give Hit (the pause is then rejected), a resume and a restart in Paused give Resuming (the restart is then rejected: a stray tap never abandons a run the player is trying to resume), and a menu and a restart give Menu (the restart is then rejected).
   4. **Timers** (restart lock, countdown).
   5. **Commit.** If the tick began in Running and the phase at its end is still Running (no accepted request, timer expiry or stall pause changed it), `dt_eff = step` and `run_time += dt_eff`; otherwise `dt_eff = 0` and `run_time` is unchanged. So the frame in which a hit, a pause, a restart, a resume or a stall happens is not counted, the ball and the tube do not move on it, and `run_ended` and `run_paused` carry the `run_time` of the last full step.
   Events are emitted synchronously as each request is accepted.
   **Settling tick.** The first tick after `run_started` and the first tick after `run_resumed` is a settling tick: `dt_eff = 0`, the stall guard does not apply and every `hit_reported` is ignored. The hitch of the reset or the transition is absorbed there, nothing moves, and Tilt Input's filter gets one more frame to settle before the first movement (rule 14).
4. **Two-step start.** A new run (from Menu, Paused or Hit) is announced as `run_reset(run_id)` and then `run_started(run_id)`. Every system resets synchronously inside `run_reset`, and `run_started` is emitted only after every `run_reset` handler has returned. Gameplay (Ball Movement advancing `s`, hazards moving) starts after `run_started`, but the first tick after it is a settling tick with `dt_eff` = 0, so nothing moves until the second tick after `run_started`.
5. **A run has an id and a clock.** `run_id` is 0 before the first run, increases by 1 on every `run_reset`, and is never reused in a session. `run_time` is the seconds spent in Running since `run_reset`, advanced only by `dt_eff`; it advances in no other phase and resets to 0 on `run_reset`.
6. **Real-time phase timers.** The restart lock and the resume countdown are measured with a monotonic clock (timestamps), never with per-frame deltas, so any freeze or slow motion (hitstop) that Juice & Feedback applies to the world cannot stall them (F3, F5). `run_time` uses world time, clamped (F1).
7. **One hit ends the run.** In Running, the first accepted `hit_reported(hazard_id, run_id)` moves the phase to Hit and emits `run_ended(run_id, hazard_id, run_time_ms)`. A hit is accepted only if its `run_id` equals the current `run_id` (senders take it from the last `run_reset` they saw), so a stale contact from the previous run, for instance one reported by the physics step after a restart teleport, is ignored, and only if the tick is not a settling tick. Every later hit request is ignored. There are no lives and no checkpoints. **Contact reports must be level-triggered.** A hit that Run State discards (stall, settling tick, Paused or an interruption) is only discarded, never remembered: the collision owner keeps reporting a hazard the ball still overlaps on every tick until one report is accepted or the overlap ends. So a contact made before a pause or a freeze is a real hit that the settling tick delays by one frame, and pausing at the moment of contact cannot erase it (Open Question 3; the mechanism belongs to the collision ADR).
8. **Hit phase and restart lock.** In Hit the world is held still and Juice & Feedback presents the hit (killer hazard isolated, art bible mood state 5). `restart_requested(press_us)` and `menu_requested(press_us)` carry `press_us`, the time of the press-down, taken with `Time.get_ticks_usec()` in the input handler. That is the only place it can be stamped (Godot input events carry no hardware timestamp: verified on 4.7.2), and it must come from one source only: with `emulate_mouse_from_touch` on (its default) one tap delivers an `InputEventMouseButton` and then an `InputEventScreenTouch` (verified on 4.7.2), so the tap owner handles `InputEventScreenTouch` `pressed` only, never both. A control that fires on release (the menu control) still forwards the press-down time. A request whose `press_us` is less than `hit_us + RESTART_LOCK` is ignored, so a panic tap at the moment of death cannot skip the sting, however late it is processed. The stamp is at most about one frame later than the touch, more if the hit frame itself hitches; that skew is accepted and is inside the `T_READ` guess (F4). A `press_us` in the future is clamped to `now_us` and a missing or non-positive one is replaced by `now_us`, each with one error log (a stamp later than the tick means the stamp and the tick use different clocks), so a bad stamp can neither bypass the lock nor block Hit forever. A press that began before the hit (a resting thumb) has an earlier `press_us` and never counts: the player lifts and presses again. `restart_unlocked(run_id)` is emitted once per Hit, at step 4 of the first tick where the lock has expired and the phase is still Hit (so not on a tick in which an accepted restart or menu request already left Hit), only so the HUD can switch its prompt from the locked to the unlocked state; acceptance depends on `press_us`, not on that event. A tap anywhere on the screen sends `restart_requested` on press-down (one thumb, no gesture, Pillar 4); the menu control fires on release and forwards the press-down time. A press that is held across the end of the lock does not convert: its `press_us` is before the unlock, so the player lifts and presses again, and the HUD's locked-state cue (UI Requirements) is what makes that visible. There is no buffering: a press is never remembered and replayed at the unlock, because the lock exists so that the player is present at the moment the game becomes ready. Hit does not time out; it waits for the player.
9. **Restart budget.** From the physical touch of an accepted `restart_requested` to the first controllable frame of the new run (the first frame presented after `run_started`) is at most `RESTART_BUDGET` (1 s; art bible: "from the player's tap"). This is the binding reading (Open Question 1: decided by the user on 2026-09-20, and the art bible line was edited to match); hit-to-controllable is only a cross-check (F4), because it includes the player's own reaction time and is tracked as a playtest metric (p50 and p95), not as a budget. The interval has two parts: `t_in`, the touch to the `press_us` stamp (measured by camera per device), and the engine part from `press_us` to that frame (F2). A personal-best banner or any results display never delays it. Each system's share is checked in F2.
10. **Pause and resume.** Running or Resuming is paused by `pause_requested(source)`, with source `button` (HUD), `back` (Android Back button), `app_interrupted` or `sensor_lost` (sent by Tilt Input's adapter when the motion sensor is lost, once per frame before the tick and never from inside a Run State handler or tick (rule 3); queued like `button`, so a run is never played on with a dead control). Paused waits for the player. In Resuming a pause is accepted from any source and returns to Paused; the HUD hides its pause button there, so in practice only `app_interrupted`, `back`, `sensor_lost` and the stall guard cause it, and the countdown has no on-screen cancel. `resume_requested` (a tap) starts Resuming: a countdown of `RESUME_COUNTDOWN` seconds with the world still frozen, then Running continues and `run_resumed` is emitted (the next tick is a settling tick); `run_time` continues where it stopped. A pause during Resuming returns to Paused and the countdown starts over next time. From Paused the player can also restart (abandoning the run) or go to the menu; either one first emits `run_abandoned(run_id, run_time_ms)`, so Scoring and Telemetry can tell a run that ended without a hit. Both carry `press_us` and are ignored when `press_us < paused_us + PAUSE_INPUT_GUARD` (0.3 s, debug log): a double tap on the pause button or a touch that lands just after the pause screen appears cannot abandon the run (F3). The guard runs from the entry to Paused, not from the player's return to the app, so it does not cover a stray touch after a call or a screen lock (Open Question 17). `resume_requested` has no guard and wins a same-tick tie against both.
11. **App interruptions and Back.** `app_interrupted` pauses a run in Running or Resuming and is applied when it is sent (rule 3). Platform Services derives it (its F1: `app_interrupted` is emitted once, when the app stops being in front and receiving input, from focus-out or application-paused, whichever comes first) and an adapter sends `pause_requested(app_interrupted)`; a duplicate is a no-op once Paused. In Menu, Paused, Hit and Boot it changes nothing. An interruption never ends a run. Android Back is delivered as `pause_requested(back)`: it pauses like the button in Running and Resuming, and is a silent no-op in every other phase (what Back does on those screens is decided by Menus & Screen Flow; Android also needs `application/config/quit_on_go_back` set to false, Open Question 16).
12. **No persistence.** Run State stores nothing between sessions; a run in progress is lost if the OS terminates the app (Open Question 6). The Player Fantasy promises only that an interruption never ends a run.
13. **Behavior, not mechanism.** How the world is frozen (engine pause, time scale, or each system stopping itself) and how hitstop is done are decided in ADRs; this GDD fixes only what happens and when.
14. **Tilt ordering guarantee.** Every `run_reset` handler returns before `run_started`, and `run_resumed` is emitted before the settling tick. So Tilt Input can capture its neutral pose in its `run_reset` handler (when the previous phase was Menu) and in its `run_resumed` handler, before anything moves; a restart from Hit or Paused keeps the previous neutral unless a steady pose far from it shows the phone moved (conditional re-anchor, Tilt Input rule 7). Its adapter learns the previous phase from the last `phase_changed` it saw (that event is emitted after `run_reset` and `run_started`, so at handler time the adapter still holds the earlier one). This does not remove an input transient by itself: a tap that jolts the phone can last several frames, so the fairness of the first second also rests on the hazard-free start that Pattern & Difficulty owes (Open Questions 11 and 17). Run State fixes only this ordering; the neutral policy and any smoothing belong to the Tilt Input GDD (Open Question 10, resolved). The grace distance before the first hazard belongs to Pattern & Difficulty (Open Question 11). A lost motion sensor reaches Run State as `pause_requested(sensor_lost)` (rule 10); Run State stays unaware of Tilt Input, and Menus & Screen Flow disables Start, Resume and Restart, and swallows the tap-anywhere restart in Hit, while the sensor is not valid (a dead sensor never burns a run).

**Requests in** (names provisional until the sender's GDD exists):

| Request | Sent by | Valid in | Result |
|---------|---------|----------|--------|

`hazard_id` is 0 or more, or -1 when the killer is unknown; any other negative value is treated as -1 with one warning.

**Events out** (integers and enums only): `run_reset(run_id)`, `run_started(run_id)`, `run_paused(source)` with source `button`, `back`, `app_interrupted` or `sensor_lost`, `run_resuming(duration_ms)`, `run_resumed(run_id)`, `run_ended(run_id, hazard_id, run_time_ms)`, `run_abandoned(run_id, run_time_ms)`, `restart_unlocked(run_id)`, and `phase_changed(new_phase, old_phase)`. For every accepted transition the specific event comes first and `phase_changed` last, after the effects are complete. Boot -> Menu and Hit -> Menu emit `phase_changed` only, and `restart_unlocked` is not accompanied by `phase_changed`. Inside any handler, `phase` already reads the new phase. Handlers must be connected directly (no `CONNECT_DEFERRED`, which would break rules 3 and 4) and must not `await` inside a `run_reset` handler.

### States and Transitions

| Phase | Meaning | World | Accepts |
|-------|---------|-------|---------|
| Boot | App started, map loading | none | `map_ready` |
| Menu | Menus shown, tube idles | idle scroll | `start_requested` |
| Running | Run in progress | live | `hit_reported`, `pause_requested` |
| Paused | Run frozen by the player or the OS | frozen | `resume_requested`, `restart_requested` and `menu_requested` (the last two after `PAUSE_INPUT_GUARD`) |
| Resuming | Countdown before play continues | frozen | `pause_requested` (any source; the stall guard also pauses) |
| Hit | Run ended by a hit, hit presented | frozen | `restart_requested`, `menu_requested` (after `RESTART_LOCK`) |

Accepted transitions (every other phase and request pair is rejected):
- Boot -> Menu on `map_ready`.
- Menu -> Running on `start_requested`.
- Running -> Hit on `hit_reported`; Running -> Paused on `pause_requested` or on the stall guard.
- Paused -> Resuming on `resume_requested`; Paused -> Running on `restart_requested` and Paused -> Menu on `menu_requested`, both only after the guard.
- Resuming -> Running when the countdown ends; Resuming -> Paused on `pause_requested` or on the stall guard.
- Hit -> Running on `restart_requested` and Hit -> Menu on `menu_requested`, both only after the lock.

## Formulas

Defaults are proposals or guesses with reasoning, not measured on a device; each guess names the measurement that will replace it.

**Shared variables**

| Variable | Symbol | Type | Range | Description |
|----------|--------|------|-------|-------------|
| Step clamp | `DT_MAX` | float | 0.1 s (shared), safe range 0.05-0.25 | The same constant as Tube Track's `t_lat`: a single source, owner to be settled in the Ball Movement GDD. Lowered from 0.25 s in the first design review (a clamped hitch moves the ball at most 25 x 0.1 = 2.5 u instead of 6.25 u); its safe range was narrowed from 0.05-0.45 to 0.05-0.25 in the second, so the largest step the clamp lets through is 25 x 0.25 = 6.25 u |
| Stall threshold | `STALL_PAUSE_THRESHOLD` | float | 0.5 s (guess), safe range 0.5-3.0, always at least 2 x `DT_MAX` | A frame whose real step is at least this long while Running or Resuming is treated as an interruption (rule 3) |
| Monotonic clock | `now_us` | int | any | `Time.get_ticks_usec()`, injected so tests are deterministic |

**F1. Run clock**

The run clock formula is defined as:

`step = min(dt, DT_MAX)` if `dt` is finite and positive, else 0. `dt_eff = step` if the tick began in Running, no stall pause happened on it, it is not a settling tick and the phase at its end is still Running (no request, timer or stall changed it), else 0. `run_time += dt_eff`, applied at the end of the tick (rule 3, step 5); `run_time_ms = round(run_time * 1000)` in events.

| Variable | Symbol | Type | Range | Description |
|----------|--------|------|-------|-------------|
| World step | dt | float | any, including NaN and inf | world-time step for this frame (`world_dt`) |
| Effective step | dt_eff | float | 0 to `DT_MAX` | the step `tick()` returns; also the step of the ball (Tube Track receives the resulting `s`) |
| Run clock | run_time | float (64-bit) | 0 to about 1e4 s | seconds in Running since `run_reset` |
| Clock in events | run_time_ms | int | >= 0 | integer form used in events |

**Output Range:** monotonic non-decreasing, 0 after `run_reset`. Only a tick that begins and ends in Running and is not a settling tick adds a step. The frame in which a hit, a pause, a restart, a resume or a stall pause happens adds 0 and the ball and the tube do not move on it, so the clock and the ball agree exactly and `run_ended` and `run_paused` carry the time of the last full step. The hitch of such a frame is never counted.
**Example:** at 60 fps, 3600 steps of 0.016667 give about 60.0 s (60.0012 with the rounded step). A stall of 0.4 s (`real_dt` from the clock, below the stall threshold): the engine caps `world_dt` at about 0.133 s (Godot 4.7.2, verified), the clamp passes 0.1 s, the clock adds 0.1 s and the ball's `s` advances 25 x 0.1 = 2.5 u, so clock and ball agree; the player loses 0.3 s of world time, never a 10 u jump. A unit test can feed `world_dt` = 0.3 directly and gets the same clamp. A frame with `real_dt` = 0.6 pauses the run and adds 0; a frame in which a hit is accepted adds 0. At 3600 s the 64-bit error is under 1e-7 s; raw `run_time` must not go into a 32-bit shader uniform (ulp 2.4e-4 s at 3600 s).

**F2. Restart budget** (a verified sum, not a limit the code enforces)

The restart budget formula is defined as:

`T_restart = t_in + t_disp + t_track + t_reset + N_present * f + t_var <= RESTART_BUDGET`; engineering gate: p95 `<= RESTART_TARGET`.

The interval runs from the physical touch to the first presented frame (rule 9). `t_in` is the part before the `press_us` stamp and is measured by camera; the rest is measured in the engine from `press_us`.

| Variable | Symbol | Default | Description |
|----------|--------|---------|-------------|
| Touch to stamp | t_in | 0.050 s (guess) | OS, driver, wait for a frame, up to the `press_us` stamp (camera-measured) |
| Run State dispatch | t_disp | 0.001 s | validate and emit |
| Tube Track `begin_run` | t_track | 0.002 s | Tube Track's own work budget |
| Other resets | t_reset | 0.013 s (guess) | Ball 1, Obstacle 5, Pattern 1, Camera 1, Score and HUD 2, Pickups and Tilt 2, Juice 1 (ms) |
| Presented frames | N_present | 3 | the frame carrying the resets, the settling tick that reads tilt, one display-pipeline frame; the 2-frame flash overlaps these |
| Frame time | f | 1 / fps, fps > 0 | real frame time |
| Variance | t_var | 0.100 s (guess) | GC, first-use shaders, spawn spikes |

**Output Range:** unbounded; it breaks the 1 s budget only below about 3.6 fps. That bound is conservative: `t_in` already includes waiting for a frame that `N_present` counts again.
**Example:** at 60 fps, 0.050 + 0.001 + 0.002 + 0.013 + 0.050 + 0.100 = 0.216 s; at 30 fps 0.266 s; at 20 fps 0.316 s. Guesses are replaced by a high-speed-camera measurement (`t_in`) and per-handler `Time.get_ticks_usec` deltas (`t_reset`).

**F3. Hit clock, unlock and pause guard**

The hit clock formula is defined as:

A restart or menu request is accepted only if `press_us - hit_us >= RESTART_LOCK_us`, with `RESTART_LOCK_us = round(RESTART_LOCK * 1e6)`. `press_us` is the press-down time stamped in the input handler (rule 8), clamped to `now_us` when it lies in the future and replaced by `now_us` when missing or not positive, each with one error. Releases and holds of a press that began during the lock never count. `restart_unlocked` is emitted once per Hit, at step 4 of the first tick where `now_us - hit_us >= RESTART_LOCK_us` and the phase is still Hit, for the HUD prompt only. The pause screen uses the same test: in Paused a restart or menu request is accepted only if `press_us - paused_us >= PAUSE_INPUT_GUARD_us`, with `PAUSE_INPUT_GUARD_us = round(PAUSE_INPUT_GUARD * 1e6)` and `paused_us` the `now_us` snapshot of every entry to Paused (from Running or from Resuming; for `app_interrupted`, which is applied between ticks, the injected clock read at the moment it is sent), so the guard starts over each time; `resume_requested` is never guarded.

| Variable | Symbol | Type | Range | Description |
|----------|--------|------|-------|-------------|
| Hit time | hit_us | int | timestamp | time Hit was entered (the tick's `now_us` snapshot) |
| Press time | press_us | int | timestamp | press-down time stamped in the input handler, carried by the request |
| Lock | RESTART_LOCK_us | int | 450,000 to 600,000 | lock in microseconds |
| Paused time | paused_us | int | timestamp | `now_us` snapshot of every entry to Paused (the clock read at send for `app_interrupted`) |
| Pause guard | PAUSE_INPUT_GUARD_us | int | 200,000 to 500,000 | guard in microseconds (default 300,000) |

**Output Range:** bool, a one-way latch per Hit.
**Example:** hit at 10,000,000 with a lock of 500,000: a press at 10,499,000 is rejected even if it is processed at 10,520,000; 10,499,999 is rejected, 10,500,000 and 10,517,000 are accepted; `restart_unlocked` is emitted at the first tick at or after 10,500,000, unless an accepted restart already left Hit on that tick. The stamp can lag the touch by about one frame (more if the hit frame hitches), so the lock can end that much early for the player; `T_READ` (F4) absorbs it. The guard follows the same rule: Paused entered at 20,000,000 with a guard of 300,000 rejects a restart or menu press stamped at 20,299,999 (debug log) and accepts one stamped at 20,300,000.

**F4. Lock bounds**

The lock bounds formula is defined as:

`LOCK_MIN = max(HITSTOP_MAX + T_READ, T_REACT + T_STOP)`; `LOCK_MAX = min(FRICTION_MAX, RESTART_BUDGET - T_restart@30fps)`.

| Variable | Symbol | Value | Description |
|----------|--------|-------|-------------|
| Longest hitstop | HITSTOP_MAX | 0.20 s | art bible mood state 5 |
| Read time | T_READ | 0.25 s (guess) | fixating on the isolated killer after grey-out; counted from `hit_us`, so it includes the display path (about 0.05 s, guess) between the tick that enters Hit and the frame that shows the sting |
| Reaction time | T_REACT | 0.25 s | simple visual reaction time |
| Panic-tap interval | T_STOP | 0.15 s (guess) | one panic tap at about 6-7 taps per second |
| Friction limit | FRICTION_MAX | 0.60 s (guess) | above this the wait reads as waiting |

**Output Range:** 0.45 s to 0.60 s.
**Example:** `LOCK_MIN = max(0.45, 0.40) = 0.45`; `LOCK_MAX = min(0.60, 1.0 - 0.266) = 0.60`. The default 0.5 s leaves 0.30 s of read time after the longest hitstop. The second term of `LOCK_MAX` is a cross-check, not the binding budget (rule 9): it keeps even the fastest hit-to-controllable (0.5 + 0.266 = 0.766 s) inside 1 s. The `T_REACT + T_STOP` term (0.40) never binds at defaults; it is the floor when reduced juice shortens the hitstop (Tuning Knobs). If `LOCK_MIN > LOCK_MAX` (for example measured `t_var` pushes `T_restart@30fps` above 0.55) the config is invalid: `LOCK_MIN` wins, so the sting is never cut, and one error is logged at startup.

**F5. Resume countdown**

The resume countdown formula is defined as:

`remaining = max(0, RESUME_COUNTDOWN - (now_us - resume_us) / 1e6)` (float division); `progress = 1 - remaining / RESUME_COUNTDOWN`; shown digit `ceil(remaining)`.

| Variable | Symbol | Type | Range | Description |
|----------|--------|------|-------|-------------|
| Countdown | RESUME_COUNTDOWN | float | 1.0 to 3.0 s (default 2.0) | length of the countdown |
| Entry time | resume_us | int | timestamp | set on every entry to Resuming, so an interruption never carries over |

**Output Range:** `remaining` in [0, RESUME_COUNTDOWN], `progress` in [0, 1]; a static helper `progress_for(duration, elapsed)` returns 1 if the duration is 0 or less (the config clamp makes that unreachable in the game, so it is tested on the helper). `run_resuming(duration_ms)` carries `round(RESUME_COUNTDOWN * 1000)`. A non-integer countdown makes the last digit shorter than the others; the HUD may show the ring alone.
**Example:** a 2.0 s countdown with 0.7 s elapsed gives remaining 1.3, digit 2, progress 0.35.

**Defaults:** `RESTART_LOCK` 0.5 s (0.45-0.60; replace with telemetry: taps rejected in the last 100 ms of the lock, and the hit-to-accepted-tap histogram); `RESUME_COUNTDOWN` 2.0 s (guess; replace with the p90 time from the resume tap until tilt angular rate settles); `RESTART_BUDGET` 1.0 s (fixed by the art bible); `RESTART_TARGET` p95 0.4 s (guess, 0.3-0.5, 2.5x headroom on the mid-tier Android target); `DT_MAX` 0.1 s (shared with Tube Track); `STALL_PAUSE_THRESHOLD` 0.5 s (guess); `PAUSE_INPUT_GUARD` 0.3 s (guess, 0.2-0.5).

## Edge Cases

**Requests and same-frame conflicts**
- **If `hit_reported` and `pause_requested(button)` arrive on the same frame in Running**: the hit wins (priority order, rule 3); the pause is then rejected because the phase is Hit.
- **If `pause_requested(app_interrupted)` arrives while a hit is still queued**: the interruption is applied when it is sent (rule 3), so the phase is already Paused when the queued hit is processed, and the hit is ignored. There is no `run_ended`: the player is never punished for the world outside the game.
- **If a stall pause and a `hit_reported` fall on the same tick**: the stall guard runs first (rule 3, step 1) and discards the hit.
- **If two or more `hit_reported` arrive on the same tick**: those with a stale `run_id` are dropped first (debug log); among the rest the one with the lowest non-negative `hazard_id` wins and `run_ended` carries it; the others are ignored, and `-1` wins only if no known id is present. The collision owner should report only the first contact; this tie-break is a deterministic fallback (Open Question 3).
- **If `pause_requested(app_interrupted)` and `pause_requested(button)` arrive on the same frame**: one pause happens and its source is `app_interrupted` (it is applied when sent, and the queued button request is then rejected in Paused). The same holds for `sensor_lost` (queued like `button`); a `hit_reported` on the same tick as `sensor_lost` wins, as with `button`.
- **If `button` and `back` arrive on the same tick**: the first in arrival order sets the source; the other is rejected.
- **If `menu_requested` and `restart_requested` arrive on the same tick in Hit or Paused**: `menu_requested` is processed first and wins (a tap on the menu button must not also start a run).
- **If `resume_requested` and `restart_requested` arrive on the same tick in Paused**: `resume_requested` wins (class priority) and Resuming starts; the restart is then rejected (debug log), so a stray tap never abandons a run the player is trying to resume.
- **If a tap arrives on the tick where the lock expires**: acceptance depends on the request's `press_us`, not on when it is processed: a press at or after `hit_us + RESTART_LOCK` is accepted, an earlier one is rejected, however late it is processed.
- **If a press began during the lock and is released after it**: it does not count; only a press whose `press_us` is at or after the end of the lock sends an accepted `restart_requested` (F3). A thumb resting on the screen through the death never counts either.
- **If a double tap sends `restart_requested` twice**: the first starts the run; the second is rejected because Running does not accept it. `run_id` increases once.
- **If `hit_reported` arrives while Paused, Resuming, Hit, Menu or Boot**: it is ignored. The world is frozen, so a late collision report cannot end a paused run. The collision owner keeps reporting an overlap that persists (rule 7), so a contact made just before the pause is delivered after the resume, and pausing at the moment of contact cannot erase a hit.
- **If `hit_reported` carries a stale `run_id`, or arrives on a settling tick**: it is ignored with a debug log (rule 7). A stale contact from the previous run can never kill the new one.
- **If `press_us` is missing, not positive or in the future**: it is replaced by, or clamped to, `now_us` and one error is logged (F3).
- **If `app_interrupted` and `restart_requested` fall on the same frame in Hit**: the interruption is a silent no-op in Hit and the restart is accepted; the new run starts normally and its settling tick absorbs the hitch of the app's return.

**Timers and app lifecycle**
- **If `now_us` repeats or goes backwards**: elapsed time is clamped to 0 or more, so a timer never finishes early (a timer anchored before a backwards jump can finish later; re-anchoring is Open Question 15).
- **If the app is backgrounded during Hit**: the phase does not change and the lock keeps using the monotonic clock. That clock may stop while the device sleeps (to verify on a device, Open Question 5), in which case the lock simply finishes later. On return `restart_unlocked` is emitted at the first tick where the lock has expired.
- **If the app is backgrounded during Resuming**: `app_interrupted` returns the phase to Paused and the countdown is discarded; the next resume starts the full countdown again.
- **If the app is backgrounded in Menu, Paused or Boot**: nothing changes.
- **If a frame's real time step is at least `STALL_PAUSE_THRESHOLD` while Running or Resuming** (a missed interruption notification, a screen-lock resume or a long stall): Run State treats it as an interruption at step 1 of the tick, discards the hits queued on that tick and gives `dt_eff` 0. A stall on the tick where a countdown would expire pauses instead of resuming. The guard covers stalls while the device is awake; the notification is the reliable path (rule 11). A hitch shorter than the threshold is clamped by F1: it costs lost time (at most `DT_MAX` of world time is played), never a jump larger than `DT_MAX` x `v_max` (2.5 u at the defaults). A hit on such a tick is accepted: the contact happened on a frame the player saw and the ball moved at most that far. This is a known limit of Fantasy #2, not a bug.
- **If a hitch of any length falls on a settling tick** (the first tick after `run_started` or `run_resumed`): it is absorbed: `dt_eff` is 0, the stall guard does not apply and hits are ignored.
- **If `dt` is NaN, infinite or negative in Running**: F1 adds 0 to `run_time` and logs one warning (at most one per second). `dt` = 0 is legitimate (Paused, hitstop) and logs nothing. A NaN, infinite or negative `real_dt` counts as 0 for the stall guard, with the same warning limit.
- **If a config value is outside its safe range, or is NaN or infinite, at startup**: it is replaced by the default (NaN and infinity only) and clamped to the nearest safe value, and one error is logged (see Tuning Knobs); Run State never runs with an unsafe lock, countdown, clamp or stall threshold.
- **If the frame rate falls below about 3.6 fps**: the 1 s restart budget cannot be met (F2). Run State does not enforce it; it is measured per device.
- **If the OS terminates the app in Running, Paused or Hit**: the run is lost and nothing is saved (rule 12).

**Pause and resume**
- **If a pause is requested on the tick the countdown expires**: the pause wins (requests come before timers) and `run_resumed` is not emitted.
- **If `resume_requested` arrives during Resuming** (double tap): rejected.
- **If a pause is requested on the first tick after `run_started`** (the settling tick): accepted, and `run_time_ms` can be 0.
- **If the player restarts or goes to the menu from Paused**: `run_abandoned(run_id, run_time_ms)` is emitted first (with 0 if no time passed); the run is dropped and not saved.
- **If a restart or menu press is stamped within `PAUSE_INPUT_GUARD` of entering Paused** (a double tap on the pause button, a touch just after the pause screen appears): it is ignored with a debug log; the guard starts over on every entry to Paused, including when Resuming returns to Paused. For a pause by `app_interrupted` the entry is the moment the interruption was sent, so a stray touch after a long call or a screen lock is outside the guard and is not covered (Open Question 17). A `pause_requested(button)` and a `restart_requested` on one tick from Running give Paused with the restart ignored (its `press_us` cannot be later than the tick's `now_us`); likewise for `menu_requested`.
- **If the pause button is pressed in Hit or Menu**: the HUD does not show it; if the request arrives anyway it is rejected. `back` in Paused, Hit, Menu or Boot is a silent no-op for Run State.

**Boot and restart**
- **If `map_ready` never arrives** (the map failed validation, see Tube Track): Run State stays in Boot and emits nothing; the loader reports the error, and a load-failure screen is Menus & Screen Flow's job. Boot time is not part of the restart budget.
- **If `start_requested` arrives in Boot**: rejected.
- **If the restart tap arrives before Juice & Feedback's hit presentation has finished**: the presentation is cut at `run_reset` (Juice clears its effects on that event), so it must be sized within the lock or be safe to interrupt.
- **If a personal-best banner is showing at restart**: it never delays the restart (art bible); the HUD treats it as non-blocking.
- **If the player never taps in Hit**: the phase stays Hit indefinitely; there is no timeout and no automatic return to the menu.
- **If the player dies again and again as fast as possible**: a cycle is strictly longer than `RESTART_LOCK` (it adds the restart time and Pattern & Difficulty's distance to the first hazard), with one flash per cycle, so the rate is below `1 / RESTART_LOCK` = 2.0 flashes per second (2.2 at the minimum lock of 0.45 s), within the 3 flashes per second cap. Nominally a cycle is about `RESTART_LOCK` + F2 = 0.72 s.

## Tuning Knobs

All defaults are proposals or guesses, not measured on a device. Every knob lives in a config resource (data-driven). Values that live in other systems are not duplicated here.

| Knob | Default | Safe range | Affects | Too high | Too low |
|------|---------|------------|---------|----------|---------|
| `RESTART_LOCK` | 0.5 s | 0.45-0.60 (F4) | How long restart and menu taps are ignored after a hit | The wait reads as waiting, against "no friction between runs" | A panic tap skips the sting and the player never reads the killer |
| `RESUME_COUNTDOWN` | 2.0 s (guess) | 1.0-3.0 | Time to re-grip the phone and settle the tilt before play continues | Friction after every pause | An unfair death right after resuming |
| `RESTART_TARGET` (p95) | 0.4 s (guess) | 0.3-0.5 | Engineering gate for the restart sum (F2); not gameplay | Little headroom on mid-tier Android | Below the 30 fps sum (0.266 s) plus margin, so unreachable |
| `DT_MAX` | 0.1 s (shared) | 0.05-0.25, same as Tube Track `t_lat` | Clamp on the run clock step (F1), the ball's step and Tube Track's window margin | A hitch moves the ball further while the player cannot see (0.25 s = 6.25 u; the default 0.1 s = 2.5 u) | A hitch is clipped early and the clock loses more time; at 0.05 a device below about 20 fps has every frame clamped and the run is permanently slower than real time |
| `STALL_PAUSE_THRESHOLD` | 0.5 s (guess) | 0.5-3.0, always at least 2 x `DT_MAX` | A single frame this long while Running or Resuming is treated as an interruption | A stall is played on as clamped steps and a hit on it is accepted (the ball still moves at most `DT_MAX` x `v_max` per frame) | An ordinary hitch pauses the run |
| `PAUSE_INPUT_GUARD` | 0.3 s (guess) | 0.2-0.5 | How long restart and menu presses are ignored after the pause screen appears (F3) | The pause screen feels unresponsive to a player who does want to abandon | A double tap on the pause button or a touch just after the pause screen appears abandons a long run |

**Fixed by other documents (not knobs):** `RESTART_BUDGET` 1.0 s (art bible mood state 5, from the player's tap); the 3 flashes per second cap (art bible).

**Derivation constants used in F4** (tune together, replace with measurements): `HITSTOP_MAX` 0.20 s (art bible), `T_READ` 0.25 s (guess, counted from `hit_us`, so it includes the display path), `T_REACT` 0.25 s, `T_STOP` 0.15 s (guess), `FRICTION_MAX` 0.60 s (guess). **Constants used in F2** (measure per device): `t_in`, `t_reset`, `t_var`, `N_present`.

**Sources of truth elsewhere** (not duplicated): the actual hitstop length and the hit presentation (Juice & Feedback), the pause button and countdown visuals (HUD), the reduced-juice setting (Settings & Accessibility).

**Interactions between knobs**
- `RESTART_LOCK` must stay at or above `LOCK_MIN` and at or below `LOCK_MAX` (F4). If `LOCK_MIN > LOCK_MAX`, `LOCK_MIN` wins. A config check also requires `RESTART_LOCK - hitstop_actual >= T_READ`, where `hitstop_actual` is a plain number injected with the config by the composition root (from Juice & Feedback's or Settings' real value; Run State never calls Juice). If the check fails, the lock is raised to `hitstop_actual + T_READ`, capped at `LOCK_MAX`, and one error is logged.
- When reduced juice shortens or removes the hitstop, `hitstop_actual` falls and `LOCK_MIN` falls with it, down to the floor `T_REACT + T_STOP` = 0.40 s. A shorter lock in that mode is an option for Settings & Accessibility, not automatic (Open Question 15).
- `STALL_PAUSE_THRESHOLD` must stay at least 2 x `DT_MAX` (always true: 0.5 s against 2 x 0.25 s), so the clamp cuts a hitch well before the stall guard pauses it, and a hitch that is clamped but not paused moves the ball at most `DT_MAX` x `v_max` (2.5 u at the default, 6.25 u at the top of the range). Whether that step can tunnel through the thinnest hazard is a check for the collision ADR (Open Question 3). Config values are validated at startup: NaN and infinity are replaced by the default, then each value is clamped to its safe range with one error logged: `RESTART_LOCK` to [`LOCK_MIN`, `LOCK_MAX`], `RESUME_COUNTDOWN` to [1.0, 3.0], `DT_MAX` to [0.05, 0.25], `STALL_PAUSE_THRESHOLD` to [0.5, 3.0], `PAUSE_INPUT_GUARD` to [0.2, 0.5].
- `RESTART_LOCK` is the lower bound of a death-to-death cycle, so it bounds the flash rate below `1 / RESTART_LOCK` per second (2.0 at defaults, 2.2 at 0.45 s); the F2 sum makes the nominal cycle about 0.72 s. A lock shorter than about 0.33 s would reach the 3 per second cap.
- `RESUME_COUNTDOWN` is independent of the other knobs. Settings & Accessibility may offer a shorter or skippable countdown (Open Question 15).

## Visual/Audio Requirements

**Visual**: Run State creates no visuals or effects itself. The hit presentation (hitstop 150-200 ms, grey-out that isolates the killer hazard, ball shards, a soft white flash of at most 2 frames and 30% opacity) belongs to Juice & Feedback (art bible section 2, mood state 5). Run State supplies only the timing contract: `run_ended` starts it, it must fit inside `RESTART_LOCK - T_READ` (0.25 s at defaults; the art bible's own maximum hitstop, 0.20 s, is the tighter bound), and it is cut at `run_reset`. The whole game stays within 3 flashes per second, with a reduced-juice setting.

**Audio**: none. The hit sting, the restart cue and any other sound belong to Juice & Feedback, and none of them may delay a restart.

## UI Requirements

Run State has no UI of its own, but four player-facing elements depend on its events. Owners are HUD and Menus & Screen Flow.
- **Pause button (HUD):** visible only in Running (hidden in Resuming, so the countdown has no on-screen cancel); sends `pause_requested(button)`; one tap, no gesture (Pillar 4); in a reachable zone but away from the resting grip, activated on release inside the button, sized to prevent accidental taps (UX spec).
- **Restart prompt (HUD or Menus):** shown from `run_ended` in a **locked state** that fills over `RESTART_LOCK` (the HUD reads the same config value and runs its own fill; the cue uses opacity and fill or a ring, not colour alone), and fully opaque with the copy "Tap" when `restart_unlocked` arrives. A press-down in Hit before `restart_unlocked` gets a non-input acknowledgement from the tap owner (for instance the ring pulses once) and is never buffered. A tap anywhere sends `restart_requested(press_us)` on press-down; a separate menu control sends `menu_requested(press_us)` and is not covered by the tap-anywhere surface: it meets the platform minimum touch target (44 pt on iOS, 48 dp on Android) but is visually small, in a screen corner away from the thumb's resting arc, fires on release inside its target and forwards the press-down time. A press that began before the hit or during the lock never counts; the player lifts and presses again. The frozen Hit frame shows the killer, the score and the delta to the personal best, with copy that avoids "Game over" and "You died" (UX spec).
- **Pause screen and resume countdown:** Paused shows resume, restart and menu (Resume is the dominant, largest thumb-zone target; restart and menu, which abandon the run, are separated from it and look inactive for `PAUSE_INPUT_GUARD` after the pause screen appears; whether abandoning a long run also needs a confirm is decided in `/ux-design`); Resuming shows the digit `ceil(remaining)` and `progress` from `run_resuming(duration_ms)`; the countdown must not rely on color alone. When the run is paused with `sensor_lost`, the pause screen shows a sensor-lost message, and Resume, Restart and the tap-anywhere restart in Hit (and Start from Menu) stay disabled or swallowed, with a "sensor not ready" cue, while Tilt Input's `valid` is false (Menus & Screen Flow reads it; Tilt Input UI Requirements).
- **Personal-best banner:** non-blocking; never delays a restart (art bible).

In Phase 4 (Pre-Production), run `/ux-design` to create a UX spec for each screen or HUD element it contributes to (pause button, restart prompt, pause screen, resume countdown) **before** writing epics. Stories that reference this UI should cite `design/ux/[screen].md`, not the GDD.

## Acceptance Criteria

Test approach: the seam (`RunStateCore` built with an injected clock and log sink, its public API, the state factory `core_in(phase)`, the signal recorder, the per-row tables and the notes carried over from the QA review) lives in `tests/unit/run_state/test-plan.md`; this section states behaviour only. Fixtures come from a constants file and factory functions; no test reads wall-clock time or real frame time; the test advances the injected clock, which starts well above 0 (a `press_us` of 0 means "missing"). Test types: **[U]** unit test in `tests/unit/run_state/` (GUT, BLOCKING); **[I]** integration test in `tests/integration/run_state/` (BLOCKING); **[V]** visual or playtest evidence in `production/qa/evidence/` (ADVISORY); **[P]** on-device measurement (evidence in `production/qa/evidence/`, ADVISORY except where stated). Defaults: `RESTART_LOCK` 0.5, `PAUSE_INPUT_GUARD` 0.3, `RESUME_COUNTDOWN` 2.0, `DT_MAX` 0.1, `STALL_PAUSE_THRESHOLD` 0.5, `RESTART_BUDGET` 1.0, `RESTART_TARGET` 0.4.

**Logic: state machine**
- **AC-1 [U]** (R1, R3): **GIVEN** a table of 6 phases x 7 requests (Hit split into locked and unlocked by `press_us` for restart and menu, Paused split into inside and after the guard for restart and menu: 46 cases; `request_pause` is sent with source `button`, `request_hit` with the current `run_id` on a tick that is not a settling tick), **WHEN** each is sent from a core built in that phase and a tick runs, **THEN** exactly **10 pairs are accepted**: Boot/`map_ready`, Menu/`start_requested`, Running/`hit_reported`, Running/`pause_requested`, Paused/`resume_requested`, Paused (after the guard)/`restart_requested`, Paused (after the guard)/`menu_requested`, Resuming/`pause_requested`, Hit (`press_us` after the lock)/`restart_requested`, Hit (after the lock)/`menu_requested`; and **36 are rejected** (phase, `run_id` and `run_time` unchanged, no event at all including `phase_changed`, exactly one log line at the level that rule 3 assigns to that pair: the test plan lists the level per row, and the 4 lock and guard cases are debug). The phase enum has exactly 6 values, starts at Boot and holds exactly one value after every case.
- **AC-2 [U]** (R3, timers): **GIVEN** 2 timers x 6 phases = 12 cases built with the state factory of the test plan, **THEN** the countdown expiry acts only in Resuming (to Running, emits `run_resumed`); the lock expiry acts only in Hit (emits `restart_unlocked` once, no phase change); the other 10 cases give no event and no log.
- **AC-3 [U]** (R3, Events out): one table row per sequence, each asserting the ordered events and their arguments, the specific event first and `phase_changed(new, old)` last: Menu -> Running `run_reset(n), run_started(n)`; Hit -> Running `run_reset(n+1), run_started(n+1)` (no `run_abandoned`); Running -> Hit `run_ended(id, hazard, ms)`; Running -> Paused and Resuming -> Paused `run_paused(source)` for each of the 4 sources (`button`, `back`, `app_interrupted`, `sensor_lost`); Paused -> Resuming `run_resuming(2000)`; Resuming -> Running `run_resumed(id)`; Paused -> Running `run_abandoned(id, ms), run_reset, run_started`; Paused -> Menu `run_abandoned(id, ms)`; Boot -> Menu and Hit -> Menu `phase_changed` only; `restart_unlocked(id)` alone, never with `phase_changed`.
- **AC-4 [U]** (R4, R14): **GIVEN** 3 doubles whose `run_reset` handlers record a return marker, **THEN** every marker precedes `run_started`, both events carry the same `run_id`, both are emitted within the tick of the accepted request (no deferral), and inside every handler `phase` already reads the new phase; `run_resumed` is emitted before the first tick of the resumed run, and that tick is a settling tick (AC-11).
- **AC-5 [U]** (R3, no nesting): **GIVEN** a mock handler on each of the 9 events that tries each of the 7 requests (63 attempts), **THEN** each attempt is rejected with one error-level log line, no phase change and no extra event; the same request sent after the handler returns produces the AC-1 outcome for that phase.
- **AC-6 [U]** (R5): `run_id` is 0 in Boot and in Menu before the first `run_reset`, increases by 1 on every `run_reset`, is unchanged by pause, resume, abandon, and by Hit -> Menu (Menu after a run holds the last id), and strictly increases over 1000 restarts; a double tap increases it once. `run_time` is 0 after a reset and advances only in Running.
- **AC-7 [U]** (R7): the first `request_hit(id, run_id)` emits `run_ended(run_id, id, run_time_ms)` exactly once; later hits are ignored; the next run ends independently. A hit whose `run_id` is the previous run's, sent on the first ticks after a restart, is ignored with a debug log and no `run_ended`. A hit on a settling tick (after `run_started` and after `run_resumed`) is ignored; the same hit on the next tick is accepted.
- **AC-8 [U]** (R2, R13): the script's own signal list (`get_script().get_script_signal_list()`, not the inherited list) is exactly `run_reset`, `run_started`, `run_paused`, `run_resuming`, `run_resumed`, `run_ended`, `run_abandoned`, `restart_unlocked`, `phase_changed`, with int or enum arguments only (verify that typed-signal reflection works in 4.7 before relying on it); the core can be built without a SceneTree; two instances share no static state; a new instance is Boot with `run_id` 0.
- **AC-9 [U]** (R2, R12, lint): a static test over the core's source finds no reference to another system's class or an autoload, no `FileAccess`, `ConfigFile` or `user://`, no `Time.` or `Engine.` call (the clock is injected), and no test-only hook in the core (the test plan builds every phase through the public API).

**Logic: timing and formulas**
- **AC-10 [U]** (F1): after a run has started and its settling tick, 3600 ticks of `world_dt` = `real_dt` = 1/60 give `run_time` = 60.0 (+/- 1e-3); `tick(0.3, 0.3)` adds 0.1 and returns 0.1; NaN, INF and -1 as `world_dt` add 0 and log at most one warning per 1.0 s of injected `now_us`; `world_dt` = 0 adds 0 and logs nothing; `run_time_ms` is 1234 for 1.2344 s; `run_time` never decreases.
- **AC-11 [U]** (F1, R3, settling tick, tick contract): `tick()` returns a non-zero `dt_eff` only on a tick that begins in Running, is not a settling tick, has no stall pause and ends in Running. The `world_dt` of a tick in which a hit, a button pause, a restart, an abandon, a countdown expiry or a stall pause happens, and of each settling tick (after `run_started` and after `run_resumed`), is not counted: `tick()` returns 0 for them and `run_time` is unchanged. `run_ended` and `run_paused` carry the `run_time_ms` of the last full step. `tick()` returns 0 in every phase except Running. `pause(button)` + `restart` on one tick from Running gives Paused with the restart ignored (inside the guard) and `dt_eff` 0; `pause(button)` + `menu` likewise.
- **AC-12 [U]** (F3, R8): **GIVEN** a hit at 10,000,000 and a lock of 500,000, **THEN** presses at 10,499,000 (processed at 10,520,000) and 10,499,999 are rejected; 10,500,000, 10,500,001 and 10,517,000 are accepted; `restart_unlocked` is emitted once over 1000 ticks and re-arms for each Hit, and is not emitted on a tick in which an accepted restart or menu request already left Hit; `menu_requested` behaves the same; a press-down stamped at 10,400,000 and still held at 10,600,000 sends no accepted request (a new press-down is needed); a `press_us` of 0 or negative is replaced by `now_us` with one error, and one in the future is clamped to `now_us` with one error.
- **AC-13 [U]** (R6): **GIVEN** 300 ticks with `world_dt` = 0, `real_dt` = 1/60 and the injected clock advancing 1/60 per tick, **THEN** the lock ends at 0.5 s in Hit and `run_resumed` fires at 2.0 s in Resuming; **GIVEN** a tick with a huge `world_dt` and `now_us` advanced by only 0.1 s, **THEN** neither timer expires.
- **AC-14 [U]** (F4, config): `LOCK_MIN` = 0.45 and `LOCK_MAX` = 0.60; the default lies inside; a lock of 0.3 is clamped to 0.45 and 0.9 to 0.60, a countdown of 0.5 to 1.0, a stall threshold of 0.2 to 0.5, `DT_MAX` of 0.02 to 0.05 and 0.4 to 0.25, `PAUSE_INPUT_GUARD` of 0.05 to 0.2 and 2.0 to 0.5; NaN and INF for each value are replaced by the default; a config with `LOCK_MIN > LOCK_MAX` uses `LOCK_MIN`; `RESTART_LOCK - hitstop_actual < T_READ` raises the lock to `hitstop_actual + T_READ` (capped at `LOCK_MAX`); each case logs one error at startup.
- **AC-15 [U]** (F5, R10): the static helper `progress_for(duration, elapsed)` and the core give rows (elapsed, remaining, digit, progress): 0 s: 2.0, 2, 0; 0.7 s: 1.3, 2, 0.35; 2.0 s: 0 and the countdown ends; 5 s: remaining clamped to 0; a duration of 0 or less on the static helper gives progress 1 and no NaN; an interruption at 1.5 s followed by a resume counts the full 2.0 s again, and `run_resuming` is emitted once per entry.
- **AC-16 [U]** (Edge, stall guard): `real_dt` 0.499 in Running does not pause; `real_dt` 0.5 in Running gives one `run_paused(app_interrupted)` and `dt_eff` 0 (`run_time` unchanged); in Resuming it returns to Paused; in Hit, Paused, Menu and Boot there is no stall pause; on a settling tick (after `run_started` and after `run_resumed`) a `real_dt` of 5.0 gives no pause, `dt_eff` 0 and ignored hits; a NaN, INF or negative `real_dt` gives no pause and at most one warning per second.
- **AC-17 [U]** (R9, R4): from an accepted restart to `run_started` is the same tick; a `run_reset` handler that advances the injected clock by 5 s still yields `run_started` in that tick, and no timer is re-evaluated in it.

**Logic: edge cases**
- **AC-18 [U]** (same tick, table-driven, one row per pair): hit + `pause(button)` gives Hit and one debug line for the pause; `pause(app_interrupted)` sent while a hit is queued gives Paused, no `run_ended`, no log line for the interruption and one debug line for the ignored hit; a stall tick + hit gives Paused, no `run_ended` and one debug line for the discarded hit; menu + restart in unlocked Hit or in Paused after the guard gives Menu and the restart is rejected (debug); resume + restart in Paused after the guard gives Resuming, the restart is rejected (debug) and there is no `run_abandoned`; `pause(button)` + restart and `pause(button)` + menu from Running give Paused and the second request is ignored inside the guard (debug); `app_interrupted` + `button` gives one pause with source `app_interrupted`; `button` + `back` gives one pause with the first's source; `app_interrupted` + restart in unlocked Hit gives Running; a pause on the tick the countdown would expire wins.
- **AC-19 [U]** (order independence): for every one of the 120 orderings of {hit, `pause(button)`, menu, restart, resume} sent in one tick, from a core forced into Running, into Paused and into unlocked Hit, the outcome (final phase, ordered events, log lines) equals the outcome listed in the test plan for that start phase (hard-coded expectations, never computed by sorting inside the test: for instance from Running a hit gives Hit, from Paused a resume wins over a restart and a menu and gives Resuming, from unlocked Hit a menu wins over a restart), with arrival order inside one class checked by separate rows (two pause sources, two restarts).
- **AC-20 [U]** (tie-break): ids {5, 2, 9} give 2; {0, 3} give 0; {-1, 4} give 4; {3, 3} give 3; {-1} gives `run_ended` with -1; {a stale `run_id` with id 0, a valid one with id 5} give 5 (the stale one is dropped first, debug log); {-5} is treated as -1 with one warning.
- **AC-21 [U]** (clock and lifecycle): a repeated or backwards `now_us` never unlocks or expires a timer early; a 30 s background in Hit stays Hit and `restart_unlocked` is emitted on the first tick; an interruption in Resuming gives Paused and the next resume takes the full countdown; `pause(app_interrupted)` and `pause(back)` in Menu, Paused, Boot and Hit change nothing and log nothing.
- **AC-22 [U]** (pause, resume, abandon, boot): run 1.0 s, pause, resume, run 0.5 s gives `run_time` 1.5 s; a second `resume_requested` in Resuming is rejected; a pause on the settling tick after `run_started` is accepted with `run_time_ms` 0; abandoning from Paused emits `run_abandoned(id, 0)` first when no time passed; a pause in Hit or Menu is rejected; without `map_ready` the phase stays Boot with no events and `start_requested` is rejected.
- **AC-23 [U]** (R11, Back): `request_pause(back)` in Running gives `run_paused(back)`; in Resuming it gives Paused; in every other phase it is a silent no-op.
- **AC-24 [U]** (flash bound, BLOCKING): **GIVEN** a bot on the injected clock at 60 fps that hits at a fixed run time and restarts at the earliest allowed press (`press_us = hit_us + RESTART_LOCK_us`), **WHEN** 300 cycles run, **THEN** every hit-to-hit interval is strictly greater than `RESTART_LOCK`, at most 2 `run_ended` events fall in any closed 1.0 s window at the default lock, and at most 3 at the minimum lock 0.45 (the art bible cap is 3 flashes per second, so the margin is zero at the minimum).
- **AC-25 [U]** (contract with doubles): **GIVEN** doubles for Ball Movement, Obstacle System, Juice & Feedback and Scoring (these check the contract only), **THEN** 1000 scripted hit and restart cycles give each double exactly one reset per run and a constant number of signal connections, and a `hit_reported` sent from a `run_started` handler is rejected.
- **AC-28 [U]** (F3, R10, Paused guard): **GIVEN** Paused entered at `paused_us` with a guard of 0.3 s, **THEN** a `restart_requested` or `menu_requested` stamped 299,999 us after `paused_us` is rejected with a debug line and no event, and one stamped at 300,000 us is accepted (`run_abandoned` first); `resume_requested` is accepted at any time and wins a same-tick tie against both; for a pause by `app_interrupted`, `paused_us` is the clock at the moment of the send (a press stamped 299,999 us after the send is rejected and one stamped at 300,000 us is accepted, whichever tick processes it); the guard starts over on each entry to Paused, including when Resuming returns to Paused; a `press_us` of 0, negative or in the future is handled as in AC-12.
- **AC-29 [U]** (R10, `sensor_lost`): `pause_requested(sensor_lost)` in Running gives `run_paused(sensor_lost)`; in Resuming it gives Paused; in every other phase it is a silent no-op with no log line; sent on the same tick as a hit it loses to the hit; sent with `app_interrupted` on one frame it gives one pause with source `app_interrupted`.
