## Overview

Scoring & Personal Best turns Ball Movement's raw distance traveled (`s`) into the one number the player actually watches: the current run's score, and whether it beat every run that came before it. It reads `s` once per frame while Running, converts it to a score by a fixed, simple rule (Formulas), and at the moment a run ends compares the final score against the stored personal best (Save & Persistence's `[scoring]` section) and writes a new one if it's higher. It is the mechanism behind game-concept.md's own Session-Level retention hook — "die → see distance/score → immediately retry, chasing a personal best" — without it, nothing on screen would ever confirm a run went further than the last, and the entire "one more run" psychology this game is built around would have nothing to point at. It decides nothing about how the score displays (HUD's job), what happens to a run that never crosses the personal best (nothing — a lower score is just a lower score), how a hazard kills the player (Obstacle System's), or when a run starts and ends (Run State's) — it owns exactly two numbers: the current run's score, and the best one ever recorded.

## Player Fantasy

**The fantasy.** Every number climbing on screen is proof I'm still going, and the moment it passes my own best is the moment I know, without needing anyone else's score to tell me, that this run already mattered (game-concept.md's Session-Level hook: "die → see distance/score → immediately retry, chasing a personal best").

**What the player feels.**
- **The number is always honest.** It only ever goes up while I'm still alive, and it stops the instant I'm not — there's no ambiguity about what it measured or when it counted (Player Motivation Profile: "direct, immediate feedback on reflex skill; visible improvement run over run"). **Scoped clarification (added this pass, game-designer):** "honest" here means honest about *distance* — it never shows ground not actually covered (Formulas explains why `floor`, not `round`, is the enforcing mechanism). It does not claim to measure dodge quality or skill expression within a run; two runs of equal survival time score identically regardless of how close any dodge was. That narrower, distance-only meaning of "honest" is deliberate and is what Open Questions 6/7 track as a still-open gap, not a promise this system silently breaks.
- **Beating my own record is the whole game.** Not a leaderboard, not another player — just me against the last version of me, which is exactly what the Bartle Achiever appeal ("beating personal best distance/score") and Pillar 5 ("lasting power comes only from player skill") both promise, and never a purchase or a grind.
- **It survives me.** The personal best I set an hour ago, or yesterday, is still there when I come back — losing this run costs me nothing but this run (Save & Persistence's own promise; this system decides *when* that promise gets triggered).

**Where "the moment I know" lives (decided fourth full-mode `/design-review`, creative-director).** The felt payoff of beating my own record is the end-of-run banner (`personal_best_updated`, Rule 6), where the full celebration is allowed. The mid-run `personal_best_passed` cue (Rule 12) is confirmation-in-flight, deliberately subtle because Pillar 1 forbids anything that could obscure an obstacle; it is not the payoff and is not expected to carry it. The score "stops the instant I'm not alive" holds for both endings alike: a voluntary quit (Rule 5) finalizes exactly as a hit does.

**Feelings to avoid.** A score that jumps or stutters in a way that doesn't match what I just did; a personal best that silently updates without me noticing I beat it, or claims I beat it when I didn't; any sense that the number is measured by something other than how far I actually got.

**Serves the pillars.** *Pillar 5, Skill First, Cosmetics Only*: the personal best is the record of skill mastery itself — nothing purchased, nothing granted, only survived and measured.

## Detailed Design

### Core Rules

1. **Score is a pure, live function of distance.** `current_score = score(s)` (Formulas F1), recomputed every frame Ball Movement's `s` is available — never accumulated or independently tracked. Score reads only Ball Movement's published `s` (Ball Movement Rule 8); it is derived, not state of its own, until a run ends (Rule 5).
2. **Live and continuous while Running.** `current_score` is published every frame after Ball Movement's own step (the same "after the step, same frame" contract Obstacle System and Near-Miss Detection already use), so HUD can show a number that climbs in real time — matching the read "die → see distance/score" (game-concept.md), which implies the score was already visible before the death, not revealed only afterward. Ball Movement's `s` is monotone non-decreasing (its own F2), so `current_score` is monotone non-decreasing across one run — it never ticks down mid-run.
3. **Reset on every new run.** `run_reset` sets `current_score` to `score(0)` = 0 synchronously, before `run_started` (mirroring Run State's own two-step start guarantee, Run State Rule 4) — so the first frame of a new run always reads 0, never a leftover value from the run before. **No other memory of `s` survives `on_run_reset()`**: the "last known-good value" that Edge Cases' guards hold is `current_score` itself, so it is 0 after a reset (never the previous run's value).
4. **Inert outside Running, by inheritance, not by special-casing.** `ScoreCore` is driven by one `step()` call per tick, in every phase, with no phase argument — it has no phase awareness of its own to branch on. Because `current_score` is a pure function of `s`, and `s` itself does not change whenever `dt_eff` = 0 (Ball Movement's own no-op contract, Ball Movement Edge Cases), `current_score` is automatically frozen in Hit, Paused, Resuming and every settling tick — no explicit phase-awareness is needed here, the same pattern Obstacle System and Near-Miss Detection already rely on for their own per-frame tests.
5. **Both a hit-ended run and an abandoned run finalize a score, identically.** On `run_ended(run_id, hazard_id, run_time_ms)` **or** `run_abandoned(run_id, run_time_ms)` (resolving Run State's open question "whether `run_abandoned` counts" as **yes**), `final_score` is the `current_score` held when the run stopped advancing. The handler uses the stored `current_score`, never re-reads `s_seam`, and never reads `hazard_id` or `run_time_ms`. **Ordering obligation:** this equals the true final distance only because (a) Run State emits the ending in its Requests stage and forces that tick's `dt_eff` to 0 (`run-state-restart.md` Frame Model), so `s` does not move on the ending tick, and (b) `ScoreService.step()` runs strictly after Ball Movement's step on every moving tick (Rule 11); if `step()` ran first, `final_score` would lag `s` by one tick. AC-22 asserts `final_score == floori(ball.s)` at ending time. A `step()` after an ending, with `s` frozen, changes nothing and fires nothing. **Accepted tradeoff:** a voluntary quit can set a personal best. Quitting is not an exploit: continuing can only match or extend the score (monotone, Rule 2), near-misses carry no bonus (Rule 8), and Juice & Feedback suppresses its celebration on the abandon path (its Core Rule 5), so a quit buys neither a safer score nor a better presentation (reasoning in the review log, 2026-09-30 third pass).
6. **A new personal best is written immediately, once per run ending, strictly greater only.** `is_new_best = final_score > personal_best` (F2) — a tie does **not** count (user decision: nothing is lost or gained by a run that matches, not beats, the record, and no save write happens for an unchanged value). If `is_new_best`, `personal_best` is updated in memory and `Save & Persistence.set_value("scoring", "personal_best", final_score)` is called immediately (mirroring Save & Persistence's own Core Rule 5, "write immediately on every change," not deferred to a flush signal), and then `personal_best_updated(final_score: int)` is emitted once for HUD/Juice & Feedback (the in-memory `personal_best` already holds the new value when the event fires). If not, nothing is written and no event fires — a run that doesn't beat the record is simply a run, not an error or a loss. **This rule has a second, unstated benefit beyond the user's own reasoning above: it makes a duplicate ending call idempotent for free.** If a driver bug ever called both `on_run_ended` and `on_run_abandoned` for the same run (Run State's own state machine is expected to prevent this — Edge Cases), the second call's `final_score` would exactly equal the `personal_best` the first call just wrote, so `is_new_best` evaluates `false` and neither a second write nor a second event occurs — no explicit re-entrancy guard is needed (SCORE-1, Acceptance Criteria).
7. **Personal best is read once, at boot, before any run exists, clamped to its declared domain.** At construction, Score reads `[scoring].personal_best` via `get_value("scoring", "personal_best", 0)`, coerces it to `int`, clamps it to `max(0, ...)` (F2's domain is `personal_best >= 0`, and Save & Persistence Core Rule 10 leaves `save.cfg` player-editable), and holds it in memory for the session; every later comparison (Rule 6) uses that in-memory value, updated in place on a new best, never re-read mid-session. A wrong-typed stored value is first handled upstream by Save & Persistence's own type-mismatch fallback (it returns the caller's default); the `int` coercion here is `ScoreCore`'s own defense (AC-18).
   **Construction contract.** `ScoreCore.new(s_seam, get_value_seam, set_value_seam, milestone_distances)`: three `Callable` **seams** (`s_seam` stands in for Ball Movement's published `s`; `get_value_seam`/`set_value_seam` for Save & Persistence's `get_value`/`set_value`) plus one **data** parameter, `milestone_distances: Array[int]` (Rule 13; `[]` means milestones disabled). A seam is something `ScoreCore` calls out through; the data parameter is only an input value. A pure `static func validate_seams(s, g, s2) -> bool` reports whether all three seams pass `Callable.is_valid()` (liveness and method existence only, never arity or return type), and `_init` calls `assert(validate_seams(...))`. **That assert is a debug-build guard only** (asserts are stripped from release exports). The real guarantee of signature and return type is the composition root binding each seam from a statically typed method reference (`save_core.get_value`, `ball_core.get_s`), never a string-built `Callable` (AC-11a).
   **Public surface.** Four command methods, called by the driver (`ScoreService`, Rule 11): `step()`, `on_run_reset()`, `on_run_ended(run_id, hazard_id, run_time_ms)`, `on_run_abandoned(run_id, run_time_ms)`; and two read-only accessors pinned as explicit methods, `get_current_score()` and `get_personal_best()`, never computed properties (so AC-11b has one closed, engine-independent target). Accessors have no side effect and are not command methods. No other constructor parameter, command method or accessor exists, and nothing near-miss-shaped is ever accepted or exposed (Rule 8). `ScoreCore` is a `RefCounted`; the composition root and `ScoreService` hold its strong references.
8. **Near-misses are not scored.** `near_miss_detected(hazard_id, run_id)` (Near-Miss Detection) is not read by this system at all — the Overview's own decision that score is distance, and distance only, closes Near-Miss Detection's own provisional "Soft" dependent line: Scoring does not consume it. A near-miss counter, if HUD or a future system wants one, is that system's own concern, not a scoring rule.
9. **No side effects beyond one write.** Score sends no requests to Ball Movement, Run State, or Near-Miss Detection; it reads their published state and events read-only, and the only thing it ever writes anywhere is `Save & Persistence.set_value` on a new personal best (Rule 6). It owns no persistence of its own beyond that one call.
10. **Deterministic.** Score is a pure function of `s` and the stored `personal_best`; it uses no randomness and, given the same sequence of `s` values and the same starting `personal_best`, always produces the same `current_score` sequence and the same final `is_new_best` verdict.
11. **Driven by a named driver, not an autoload.** A thin `ScoreService` node in the main scene (mirroring Save & Persistence's `SaveService`) calls `ScoreCore.step()` once per tick and connects Run State's `run_reset`/`run_ended`/`run_abandoned` to `ScoreCore`'s three handlers. **Obligations on the game-loop ADR** (`run-state-restart.md` Open Question 4): `step()` runs strictly after Ball Movement's step on every moving tick (Rule 5), and both use the same callback type (`_physics_process` vs `_process` must match, or "same frame" is false). **Connection timing:** `ScoreService` connects during composition-root construction and never with `CONNECT_DEFERRED`, so Rule 3's zeroing runs in the emission's own call stack. Godot drops a signal emitted before `connect()`; Run State emits nothing until an external `map_ready` request that follows construction (`run-state-restart.md` Core Rule 15), so no emission is missed. AC-19 proves the wiring against a fake source, AC-22 against the real Run State. **Subscriber order:** this driver's `run_ended` handler is registered in the position Run State's pinned list gives it (`run-state-restart.md`, Subscriber order): second, after Juice & Feedback and before HUD, and `personal_best_updated` is emitted synchronously inside that handler, so Juice's `run_ended` handler has already run when it arrives. Scoring depends on that list and does not define its own order; `run_reset` handlers are likewise registered in the pinned order. No ordering is promised for any event or subscriber outside Run State's pinned list. **No autoload** (coding standards: dependency injection over singletons). **Signals:** `personal_best_updated(final_score: int)`, `personal_best_passed(personal_best: int)`, `milestone_crossed(threshold: int)` declare typed parameters as documentation only; Godot does not enforce signal parameter types at emit, so subscribers must also type their handlers `int`.
12. **A live personal-best crossing fires once per run, HUD-only, non-occluding.** The frame `current_score` first exceeds the in-memory `personal_best` during a run (`current_score > personal_best`, strictly, matching F2), `ScoreCore` emits `personal_best_passed(personal_best: int)` exactly once for that run — a separate, earlier signal from the end-of-run `personal_best_updated` (Rule 6), which still fires at `run_ended`/`run_abandoned` as before with the full celebration. `personal_best_passed` carries no screen-space presentation of its own: HUD's own consumption (Dependencies) is limited to a non-occluding, HUD-local acknowledgment (e.g. the `personal_best` digit flashing or changing color once) — no FOV punch, no bloom, nothing that could obscure an obstacle (Pillar 1) mid-run. **Whether a haptic pulse accompanies this acknowledgment is not this GDD's call to make (corrected 2026-09-30)**: haptic doesn't obscure anything visually, so Pillar 1 is not actually the relevant constraint here — the real concern is channel collision with Pillar 3's own near-miss haptic vocabulary, which `juice-feedback.md` owns. The include/exclude decision on a haptic pulse for `personal_best_passed` belongs to `juice-feedback.md`/`hud.md`, not here; this GDD only commits to "no occluding visual effect." A single boolean latch (`has_passed_this_run`) tracks whether the signal has already fired for the current run, cleared on `run_reset` alongside `current_score` (Rule 3) — a run that dips back below `personal_best` is impossible today (`current_score` is monotone non-decreasing), but the latch, not a re-check of the comparison every frame, is what actually prevents a second fire. **`personal_best_passed` never fires while the in-memory `personal_best` is exactly 0 at the moment of the crossing** (user decision) — a stored best of 0 means no real run has ever set one yet (Rule 7's own default for a fresh install), so there is nothing genuine to have passed, and firing here would turn Rule 12's promised "the moment I know I beat my own record" into meaningless noise on literally the first tick of the first run a fresh install ever plays. This check reads the current in-memory `personal_best` value at crossing time, not a separate latch, so it stops suppressing correctly the instant any run's ending writes a real nonzero best (Rule 6) — including a later run within the same session that never re-reads from disk (Rule 7). A brand-new player's first run therefore gets no `personal_best_passed` flash; `milestone_crossed` (Rule 13) still fires normally on it, a weaker, impersonal signal and not a substitute. A first-run-specific cue is HUD's call (Open Question 11).
13. **A distance milestone fires once per threshold, per run, live (added 2026-09-30 — restores `game-concept.md`'s own Short-Term Loop promise: "distance milestones (e.g., 100m, 250m)", which no GDD had implemented).** `MILESTONE_DISTANCES` (Tuning Knobs) is an ascending array of positive integer thresholds in score units (**1 u = 1 m**, so a threshold is a displayed score), delivered to `ScoreCore` as its fourth constructor parameter `milestone_distances` (Rule 7). The frame `current_score` first reaches or passes a threshold not yet crossed this run, `ScoreCore` emits `milestone_crossed(threshold: int)` exactly once for that threshold, via `while next_milestone_index < milestone_distances.size() and current_score >= milestone_distances[next_milestone_index]` (a `while`, not an `if`, so several thresholds can fire in one call). A single index latch (`next_milestone_index`, starting at 0, cleared to 0 on `run_reset` alongside `current_score`, Rule 3) tracks the next uncrossed threshold — the same once-per-run latch pattern Rule 12 already established for `personal_best_passed`, applied to a sequence of thresholds instead of one. If a single `step()` call's `current_score` jump crosses more than one threshold at once (a large `s` delta), `milestone_crossed` fires once per crossed threshold, in ascending order, within that same call — no threshold is ever silently skipped or batched into one event. **This is a coarse, fixed-interval progress signal, not a skill-expression one** — it does not answer Open Questions 6/7 (whether distance-only scoring carries a within-run signal for dodge quality), which stay open for that narrower gap; it only restores the periodic pacing beat the concept doc promised, and gives HUD/Juice & Feedback a mid-run beat that fires for every player, not only ones already near their own personal best (unlike `personal_best_passed`, Rule 12).

### States and Transitions

Score has no phase of its own; its behavior is a function of `dt_eff` and Run State's events, exactly the pattern Ball Movement already uses.

| Situation | Event / `dt_eff` | Score does |
|-----------|------------------|-----------|
| Boot | none | Reads `personal_best` from Save & Persistence (Rule 7); `current_score` = 0 (well-defined, not undefined — no run has started yet) |
| New run | `run_reset` | `current_score` = 0 (Rule 3) |
| Running, `dt_eff` > 0 | every step | `current_score` = `score(s)`, published continuously (Rules 1-2) |
| Hit, Paused, Resuming, settling tick | `dt_eff` = 0 | `current_score` frozen at its last value (Rule 4) |
| Run ends by hit | `run_ended` | `final_score` captured; compared against `personal_best` (Rule 6) |
| Run ends by abandon | `run_abandoned` | Same as `run_ended` (Rule 5) |
| Running, a threshold in `MILESTONE_DISTANCES` is crossed | every step | `milestone_crossed(threshold)` fires once per crossed threshold (Rule 13) |

## Formulas

**Why no `DISTANCE_SCALE` knob.** The score is literally the world-unit distance traveled, not a stylized derivative of it — Section B's "the number is always honest… no ambiguity about what it measured" promise means a scaling multiplier would divert the displayed number from what Ball Movement actually reports, for no motivating problem today (Ball Movement's own F2 worked example already climbs into the hundreds/thousands within a couple minutes at defaults, which reads fine unscaled). If playtesting later shows the raw number feels wrong, a scale knob can be added then, as a deliberate, evidenced change.

**F1. Score conversion**

```
current_score = floor(s)
```

**Implementation note:** GDScript's global `floor()` returns a `float`, not an `int` — assigning it directly to `current_score` (a statically-typed `int` per the type table below) needs `floori(s)` (which returns `int` directly) or the explicit cast `int(floor(s))`; either produces an identical result for `s >= 0` (Formulas' own declared domain), so this is a typing note, not a behavioral choice. **Ordering obligation, pinned this pass** (third full-mode `/design-review`, godot-specialist): converting a non-finite `s` (`NaN`/`INF`) through `floori()`/`int(floor())` does not raise a catchable error in GDScript — the underlying float-to-int64 conversion is undefined-behavior-adjacent and can silently produce a garbage integer rather than throwing. Edge Cases' "never propagates `NaN`" guarantee therefore depends entirely on `ScoreCore.step()` checking `is_finite(s)` **before** ever calling `floori()`/`floor()`, never on any safety net from the conversion itself — an implementation that floors first and checks after does not satisfy this GDD, even if it happens to pass AC-15 by luck on a given platform. **Int64-range extension (fourth full-mode `/design-review`, systems-designer):** `is_finite()` rejects only `NaN`/`INF`, so a finite `s` above int64 max (e.g. `1e19`) would still hit the same undefined conversion. The guard is therefore `is_finite(s) and s >= 0.0 and s <= 9.2e18` (a constant safely below `2^63 - 1`), and an `s` above it is treated as one more no-op frame holding `current_score` at its last known-good value, identical to the other out-of-contract cases in Edge Cases. Unreachable in legitimate play (about a billion times past `s`'s own `2^53` precision ceiling), so this is symmetry with the other guards, not a live risk.

| Symbol | Type | Range | Description |
|--------|------|-------|-------------|
| `s` | float64 | `>= 0`, monotone non-decreasing during a run | Ball Movement's published distance traveled (Ball Movement Core Rule 8, F2) |
| `current_score` | int | `>= 0`, monotone non-decreasing during a run | The live score value published every frame (Rule 1) |

**Output range:** integer `>= 0`, with no meaningful practical ceiling. `current_score` is a GDScript `int` (64-bit signed), exact up to `2^63 - 1` — a footnote for completeness (added this pass): `2^63 - 1` is itself about a billion times larger than `s`'s own `2^53` float64-precision ceiling discussed below, so the int's own range is never the limiting factor at any point this GDD needs to reason about; the practical bound here is not the int's own range but `s`'s, since `s` is a `float64` whose mantissa loses sub-1.0 resolution once `s` grows past `2^53` (about 9 quadrillion u, at which point `floor(s)` degrades gracefully — it stays well-defined, never `NaN`/negative/wrong-typed — rather than losing precision catastrophically). At `V_MAX` = 25 u/s, `2^53` u is roughly 11 million years of continuous play, so Scoring introduces no cap of its own and needs none; the earlier claim in this Formula that the *int* was exact only to `2^53` was a misattribution corrected this revision — the int's own range is far larger, but irrelevant, since `s` (the float64 input) is the actual limiting factor and is nowhere close to it at any realistic session length. (`S_PRECISION_LIMIT` = 16384 u, ~682 s, is **Tube Track's** own constant — a float32 world-Z rendering-jitter warning threshold for placing `Vector3` positions, unrelated to `s`'s float64 accumulation or to this integer score; it does not apply here and is not a ceiling on `current_score`.) Since `s` never decreases (Ball Movement F2) and `floor` is monotone non-decreasing, `current_score` provably never decreases mid-run, including at integer-boundary frames, and — as of this revision — even on a tick where Ball Movement's own contract is violated and `s` decreases anyway, since Edge Cases now guards that case symmetrically with the existing non-finite/negative-`s` guards; there is no rounding artifact and no out-of-contract input that can make it flicker down. `floor`, not `round`, is deliberate: `round` would tick the score up to 10 while `s` is still 9.6, showing distance the player hasn't actually covered yet, which would violate Player Fantasy's "the number is always honest."

**Example** (Ball Movement F2's own worked values, `V_START` = 10, `V_MAX` = 25, `T_RAMP` = 90): `s(45)` = 618.75 → `current_score` = 618; `s(90)` = 1575 → `current_score` = 1575 exactly (an integer `s` value floors to itself, no artifact); a frame where `s` advances from 1574.991 to 1575.008 publishes `current_score` 1574 then 1575 — one clean increment, never a double-tick or a flicker back.

**F2. New-personal-best comparison**

```
is_new_best = final_score > personal_best
```

| Symbol | Type | Range | Description |
|--------|------|-------|-------------|
| `final_score` | int | `>= 0` | `current_score` captured at `run_ended`/`run_abandoned` (Rule 5) |
| `personal_best` | int | `>= 0`, default 0 | In-memory stored best; read once at boot via `get_value("scoring", "personal_best", 0)` (Rule 7), updated and persisted only on a new best (Rule 6) |
| `is_new_best` | bool | `{true, false}` | Whether this run's `final_score` strictly beats the stored best |

**Output range:** boolean; no clamping applicable.

**Boundary cases.** **Fresh install, first run ever, `final_score` = 0**: `personal_best` defaults to 0 (Rule 7), so `is_new_best = (0 > 0) = false` — a zero-distance run does not count as a new best against a zero default; this falls directly out of the locked "strictly greater, no ties" rule (Rule 6) with no special-casing needed. **Is `final_score` = 0 actually reachable?** Yes, but only via `run_abandoned`, not `run_ended`: Ball Movement Rule 5 guarantees the segment from `s` = 0 to at least 11 u is hazard-free (the reset-glide guarantee), so a hit-ended run can never have `s` = 0. A player can, however, back out to the menu on the very first settling tick after `run_started` — before any moving step (Ball Movement's own States table: the first tick after `run_started` has `dt_eff` = 0, nothing moves) — making `run_abandoned` fire while `s` is still exactly 0. F1 and F2 both handle this with no special-casing: `current_score` = `floor(0)` = 0, and F2 correctly rejects it as a best (or trivially fails against any nonzero existing best). Any later run ending at `final_score` = 0 against a nonzero `personal_best` also correctly evaluates `false` — the formula needs no additional guard for "empty" runs at any point in the session. `personal_best`'s own declared domain above (`>= 0`) is enforced once, at read time (Rule 7's clamp), not by this formula — F2 itself assumes a valid non-negative `personal_best` and is not responsible for sanitizing it (Edge Cases, AC-18).

**Worked example:**

| Case | `final_score` | `personal_best` (before) | `is_new_best` | `personal_best` (after) |
|---|---|---|---|---|
| Fresh install, instantly abandoned | 0 | 0 (default) | false | 0 (unchanged, no write) |
| Fresh install, first real attempt | 342 | 0 (default) | true | 342 (written) |
| Next run, worse | 200 | 342 | false | 342 (unchanged) |
| Next run, exact tie | 342 | 342 | false | 342 (unchanged, no write — Rule 6) |
| Next run, beats by 1 | 343 | 342 | true | 343 (written) |

## Edge Cases

- **If a run is abandoned before any moving step (`s` still exactly 0)**: `final_score` = `floor(0)` = 0; `is_new_best` is `false` against any `personal_best` (F2) — a zero-distance run is never a new best, including on a fresh install where the default `personal_best` is also 0.
- **If a run's `final_score` exactly ties `personal_best`**: `is_new_best` is `false` (F2, strictly greater only) — `personal_best` is not rewritten, no `personal_best_updated` event fires, and no `Save & Persistence.set_value` call happens for an unchanged value (Rule 6).
- **If `Save & Persistence.set_value("scoring", "personal_best", final_score)` fails (disk full, permission error — `WRITE_FAILED`)**: the in-memory `personal_best` this system holds is still updated to the new value (Save & Persistence's own Core Rule 6 guarantee: "the in-memory value is still updated"), and `personal_best_updated` still fires for HUD/Juice & Feedback within the current session — only a cold boot before the next successful write would read back the old, lower value from disk. This system does not retry or special-case the failure; it trusts Save & Persistence's own contract and rate-limited logging (Save & Persistence Rule 2, Edge Cases).
- **If Ball Movement ever publishes a non-finite `s`**: treated as a no-op frame, holding `current_score` at its last known-good value (mirrors Near-Miss Detection's own guard against a non-finite `theta`/`s`) — never propagates `NaN` into `current_score`, `final_score`, or a save write.
- **If Ball Movement ever publishes a negative, finite `s`** (violating its own declared `>= 0` domain — Ball Movement Core Rule 8, F2): treated identically to a non-finite `s` above, a no-op frame holding `current_score` at its last known-good value — this system does not clamp or otherwise sanitize `s` itself, since a negative `s` is exactly as out-of-contract as `NaN`/`INF` and gets the same defensive response, keeping `current_score`'s own `>= 0`, monotone-non-decreasing guarantee intact without a second sanitization path (new this revision, symmetric with the negative-`personal_best` clamp below).
- **If Ball Movement ever publishes a valid, finite, non-negative `s` whose score is lower than the one already held** (e.g. `s` goes 500 to 490 with no `NaN` or negative value between, violating Ball Movement's monotone promise, Core Rule 8/F2): a no-op frame holding `current_score`. The guard order in `step()` is `is_finite(s) and s >= 0.0 and s <= 9.2e18`, then `floori(s)`, then `floori(s) < current_score` holds. It compares against `current_score` itself and keeps **no separate `last_s` tracker**, so `on_run_reset()` (Rule 3) clears it automatically and a new run whose `s` restarts at 0 is never mistaken for a decrease. The "last known-good value" of the non-finite, negative and over-range guards is likewise `current_score`: a `NaN` first step after a reset holds 0, never the previous run's value. A held frame leaves everything unchanged and the next valid value recovers (`500, 490, 495, 510` publishes 500, 500, 500, 510). Chosen over weakening F1's "never decreases" proof: every upstream contract violation gets the same defensive response regardless of cause. The `9.2e18` bound is crash-safety only; a finite spike below it is not defended against (Ball Movement's own tests own that).
- **If `run_reset` arrives while a prior run's score was never finalized**: does not happen under Run State's own state machine — every path back to `run_reset` for a run that had actually started passes through either `run_ended` (Hit → restart, after the lock) or `run_abandoned` (Paused → restart or menu, Run State Rule 10) first, so `current_score` is always finalized (Rule 5) before it resets (Rule 3). This system adds no defensive check for an out-of-order sequence, since Run State's own rules already forbid it.
- **If no save file exists yet (first-ever launch)**: `get_value("scoring", "personal_best", 0)` returns the caller's default, 0 (Save & Persistence's own Edge Cases: "not an error... every `get_value` call returns the caller's default") — this system treats a fresh install identically to a session where `personal_best` happens to be 0, with no special first-launch logic of its own.
- **If `personal_best` read from Save & Persistence is negative (a hand-edited or corrupted-but-type-valid save file — Save & Persistence's own Core Rule 10 leaves `save.cfg` unsigned)**: clamped to 0 at read time (Rule 7) before any comparison — F2's own declared domain is `personal_best >= 0`, and without this clamp a negative value would make `is_new_best` evaluate `true` even for a zero-distance run, contradicting Boundary Cases' own "a zero-distance run is never a new best" claim. This is the one state Save & Persistence's own scope decision (Rule 10: "a player who edits it directly can only ever defraud themselves") deliberately leaves open, so the clamp is closing a foreseeable input, not over-engineering against a hypothetical one.
- **If `personal_best` read from Save & Persistence is an excessively large hand-edited value (e.g. near `int64` max) instead of negative**: deliberately *not* clamped or guarded, asymmetrically with the negative case above — and that asymmetry is intentional, not an oversight (added 2026-09-30). A negative stored value breaks F2's own declared domain and makes `is_new_best` evaluate incorrectly (`true` when it should be `false`), so it must be corrected before use. An excessively large one stays a well-typed, non-negative int and every comparison against it still evaluates exactly as F2 defines — it can only ever make every future run's `is_new_best` come back `false`, i.e. the player defrauding only themselves out of ever seeing `personal_best_updated` again, exactly the class of self-inflicted edit Save & Persistence's own Rule 10 already accepts as in-scope-but-unprotected. No guard is added here because none is needed to preserve F2's correctness domain.
- **If `current_score` crosses more than one `MILESTONE_DISTANCES` threshold within a single `step()` call** (a large `s` delta, e.g. after a settling tick or a clamped hitch): `milestone_crossed` fires once per crossed threshold, in ascending order, all within that same call — never batched into a single event and never silently skipped (Rule 13).
- **If `personal_best` is 0 (fresh install, or any session where no real best has ever been written) and the very first run's `current_score` immediately exceeds 0**: `personal_best_passed` does not fire (Rule 12's own suppression) — there is no real best yet to have passed, so the signal stays silent through the entire first run regardless of how far `current_score` climbs; the end-of-run `personal_best_updated` (Rule 6) still fires normally once that run ends, writing the first real best.
- **If both `on_run_ended` and `on_run_abandoned` are somehow called for the same run (a driver bug — Run State's own state machine is expected to prevent this, the same class of impossibility as the `run_reset`-while-unfinalized case above)**: the second call's `final_score` already equals the `personal_best` the first call just wrote, so `is_new_best` evaluates `false` (F2, strictly greater) and neither a second `Save & Persistence.set_value` call nor a second `personal_best_updated` fires — a free consequence of Rule 6's strictly-greater comparison (SCORE-1, Acceptance Criteria), not a defended invariant of its own.

Tests live in `tests/unit/scoring_personal_best/` and `tests/integration/scoring_personal_best/`, named `scoring_personal_best_[feature]_test.gd`. Exact `==` for `current_score`/`final_score`/`personal_best` (all integers) and `is_new_best` (bool); a fresh core per case.

**Fixture:** `PERSONAL_BEST_FIXTURE_DEFAULT` = 500 (deliberately nonzero and different from this GDD's own worked-example values of 0/342, so no `ScoreCore`-driven AC can pass against a hardcoded example number — `ScoreMath`'s own static truth tables, AC-1 and AC-3, are a separate concern not covered by this fixture default, addressed instead by the non-worked-example rows each of those ACs adds below). `make_score_fixture()` — **clarified this pass** (third full-mode `/design-review`, qa-lead flagged it as a previously dead/unused spec): a convenience wrapper returning `make_core(make_s_stub([]), make_save_stub(PERSONAL_BEST_FIXTURE_DEFAULT))`'s three seams already bound — i.e. a fresh `ScoreCore` constructed against the default `personal_best` (500) and an empty `s` sequence, for any AC that needs a ready core and doesn't care about a specific starting `personal_best` or `s` script of its own (most `[C]`-tier ACs either call this or build their own via `make_core` directly when they need a non-default `personal_best`). `make_s_stub(sequence: Array[float])` returns an `s_seam` `Callable` that returns the next scripted value on each call, holding the last value forever once the sequence is exhausted (simulating a frozen `s`); an empty sequence returns 0.0. The stub keeps its index, and the spies keep their counters, in a member or container (GDScript closures capture primitive locals by value, so a captured counter would never advance). `make_signal_log(core)` returns a recording array connected to all three of `ScoreCore`'s signals, storing `(name, payload)` in emission order, for the ACs that assert signal count, payload or order. `make_save_stub(initial_best, write_succeeds := true)` returns a `get_value_seam`/`set_value_seam` pair with call-count and call-argument spies. `make_core(s_seam, get_value_seam, set_value_seam, milestones: Array[int] = [])` constructs a fresh `ScoreCore`; the first three are its seams and the fourth its data parameter (Core Rule 7); the four public command methods (`step()`/`on_run_reset()`/`on_run_ended()`/`on_run_abandoned()`) and the two accessor methods (`get_current_score()`/`get_personal_best()`) are called directly on the `ScoreCore` instance `make_core(...)` returns, never passed into it.

**Driver-level fixture, for AC-19 only (added this pass — qa-lead flagged AC-19 as unimplementable without it):** `make_fake_run_state()` returns a minimal signal source exposing exactly three signals — `run_reset(run_id)`, `run_ended(run_id, hazard_id, run_time_ms)`, `run_abandoned(run_id, run_time_ms)` — and no other Run State behavior; it exists only to be emitted from directly in a test, standing in for the real `RunState`. `make_score_service(core: ScoreCore, source) -> ScoreService` constructs a `ScoreService` around the given `ScoreCore` and connects it to `source`'s three signals exactly as Rule 11 describes (composition-root-style, non-deferred), returning the constructed `ScoreService`; AC-19's assertions are then made by spying on the `core` passed in (e.g. confirming `on_run_reset()` was invoked on it) rather than on `ScoreService` itself, which has no public state of its own beyond the connection.

**F1 — floor and monotonicity**
- **AC-1 [M]** `score(s)`: `0 -> 0`; `9.999 -> 9`; `10.0 -> 10`; `10.5 -> 10`; this GDD's own worked pair `1574.991 -> 1574`, `1575.008 -> 1575`; and a non-worked-example value, `777.3 -> 777` (closing the residual hardcoding risk the Fixture's own rationale doesn't cover for this static truth table). A mutation substituting `round()` for `floor()` must fail both the `9.999` and `10.5` rows, for different reasons: for `9.999` it returns `10` (distance not yet covered); for `10.5`, GDScript's `round()` is round-half-away-from-zero, so it returns `11`, overshooting even further — both violate F1's own "always honest" reasoning.
- **AC-2 [M]** Monotonicity property: over a fixed table of at least three scripted non-decreasing `s` sequences covering flat runs (duplicate values) and fractional-to-integer boundary crossings, the resulting `score(s)` sequence is non-decreasing at every step and `score[i] - score[i-1] <= ceil(s[i] - s[i-1])` at every step. A mutation that ever produces a lower score for a later, equal-or-greater `s` must fail.

**F2 — strictly-greater comparison**
- **AC-3 [M]** `is_new_best(final_score, personal_best)` table: `(0, 0) -> false` (fresh-install, zero-vs-zero); `(342, 0) -> true`; `(200, 342) -> false`; `(342, 342) -> false` (exact tie); `(343, 342) -> true`; and a non-worked-example pair, `(9001, 9000) -> true` (same rationale as AC-1's added row: `PERSONAL_BEST_FIXTURE_DEFAULT` only protects `ScoreCore`-driven ACs, not this static truth table). A mutation using `>=` instead of `>` must fail the tie row.

**Live/frozen behavior (Rules 1, 2, 4)**
- **AC-4 [C]** Live update while `s` advances: feeding a scripted advancing `s` sequence through `step()` once per tick publishes `current_score = floor(s)` on every tick, matching AC-1's per-value expectations exactly — proving continuous recompute, not an accumulator (a mutation that adds/accumulates deltas instead of recomputing `floor(s)` fresh must fail once a tick's `s` delta and its floor delta disagree).
- **AC-5 [C]** Frozen when `s` stops advancing (Rule 4, "by inheritance, not special-casing"): feed a sequence where `s` repeats the same value for several consecutive `step()` calls (simulating Hit/Paused/Resuming/a settling tick) — `current_score` holds its last value across every one of those ticks. `ScoreCore.step()` accepts no phase argument at all, so this must hold with zero phase-aware branching.

**Reset (Rule 3)**
- **AC-6 [C]** `on_run_reset()` after a prior run left `current_score` nonzero: `current_score` reads exactly `0` synchronously, immediately after the call returns, with zero further `step()` calls needed — matching "the first frame of a new run always reads 0." **Reset clears the guards' memory (Rule 3, Edge Cases):** run to `s` = 1575, `on_run_reset()`, then `s` = 0, 0.5, 3.0, 12.0 publishes 0, 0, 3, 12 (never held at the old maximum); a `NaN` first step after the reset holds 0, never 1575.

**Finalization — both endings identical (Rule 5)**
- **AC-7 [C]** Two parallel scenarios reach the same `current_score` via an identical scripted `s` sequence; one calls `on_run_ended(run_id, hazard_id, run_time_ms)`, the other calls `on_run_abandoned(run_id, run_time_ms)` — both produce an identical `final_score` (equal to the pre-ending `current_score`) **and** an identical `is_new_best` verdict against the same starting `personal_best` **and** an identical `set_value_seam` call count/argument **and** an identical `personal_best_updated` firing count — all four, not just the first two, since Rule 5's own "identically" covers the write/event side effects too, not only the computed values. A mutation that makes `on_run_abandoned`'s handler diverge from `on_run_ended`'s in call count or argument on any of these four must fail. A companion row fires **only** `on_run_abandoned` (never `on_run_ended`) and asserts `final_score`/`is_new_best` are still produced, not silently skipped — a mutation that listens to only one of the two events must fail this row. A third row varies `hazard_id` and `run_time_ms` across otherwise-identical runs and asserts neither value ever changes `final_score` or `is_new_best` — both handler signatures accept them, but Rule 5 states neither is read for scoring. A fourth row repeats the same paired-scenario structure for the **non-new-best** branch (`final_score` below the starting `personal_best`): both endings still produce an identical `final_score` and an identical `is_new_best = false` verdict, **and** both agree on zero `set_value_seam` calls and zero `personal_best_updated` firings — proving the "identically" guarantee holds on the write/event side even when neither ending writes or fires anything, not only on the new-best path the first three rows exercise.

**Write-only-on-a-new-best (Rule 6)**
- **AC-8 [C]** Three endings against `PERSONAL_BEST_FIXTURE_DEFAULT` = 500: (a) `final_score` = 600 (beats it) → `set_value_seam` called exactly once with the new value, `personal_best` updates in memory, `personal_best_updated` fires exactly once with payload 600, `get_personal_best()` already reads 600 when it fires, and the write arguments are `("scoring", "personal_best", 600)`; (b) `final_score` = 500 (tie) → zero `set_value_seam` calls, no event, `personal_best` unchanged; (c) `final_score` = 400 (below) → zero `set_value_seam` calls, no event. (b) and (c) also assert `get_personal_best()` still reads 500, so a mutation assigning `personal_best = final_score` unconditionally fails. A mutation that writes on every ending must fail (b)/(c); a mutation that never writes must fail (a).

**Boot read-once (Rule 7)**
- **AC-9 [C]** Construct a core against `make_save_stub(500)`; repeat N times: `on_run_reset()` → several `step()` calls → an ending call that beats the running best (raising `personal_best` in memory each cycle). `get_value_seam` is called **exactly once**, at construction, across the entire scripted session — including every `on_run_reset()` in between — never again, even though `set_value_seam` is called on every new-best ending.
