## Overview

Pattern & Difficulty owns *which* hazards appear where, in what sequence, and how that sequence gets harder as a run goes on. It implements Obstacle System's `HazardContentProvider` interface directly: a hand-authored library of **chunks** — short, pre-designed hazard arrangements, each a deliberate puzzle with a learnable solution — sequenced procedurally by a **difficulty weight** that rises with `run_time`, so early chunks are sparse and single-type and later chunks are denser, faster-paced, and mix more hazard types together. It is never played directly and has no interface of its own beyond that one function call, yet it is the system every other GDD has been waiting on: Obstacle System's own preflight gates (`GAP_MIN`, `TOO_DENSE`, `MAX_PIECES_PER_SEGMENT`) exist specifically to constrain what this system is allowed to author, and Tube Track's F9 visibility budget needs a real `T_dodge_worst` from here to stop being a placeholder. It exists because without it there is nothing to dodge that means anything: Obstacle System tests collision against whatever this system hands it, but decides nothing about *whether that arrangement is fun, fair, or learnable* — and game-concept.md's own predicted player behavior, "players will mentally chunk obstacle patterns after repeated deaths, recognizing recurring shapes rather than reacting cold each time," only happens if chunks actually *repeat* in a recognizable way, which requires an author, not a random generator. It decides nothing about hazard geometry or collision (Obstacle System's), nothing about how fast the ball moves or turns (Ball Movement's), nothing about how a hazard looks (Environment & Theming's, guided by the art bible), and nothing about score (Scoring & Personal Best's, unauthored) — it owns exactly one output: an ordered, escalating sequence of pre-authored puzzles.

## Player Fantasy

**The fantasy.** The game keeps asking more of me, and every time it does, I can feel *why* — never a cheap trick, always a puzzle I could have solved if I'd read it right (Pillar 2: "every death traces back to the player's own choice or reaction, never to randomness or bad luck").

**What the player feels.**
- **Recognition is a real edge.** The second time I see a pattern, I already know the line — not because I memorized a script, but because the shape taught me something the first time (game-concept.md's own predicted dynamic: "players will mentally 'chunk' obstacle patterns after repeated deaths, recognizing recurring shapes rather than reacting cold each time").
- **Harder never means unfair.** As a run goes on, the puzzles get denser and faster, but I never feel ambushed — the escalation is smooth enough that I can always point to the exact moment I stopped keeping up, and it's always my reaction time, never a spike I couldn't have seen coming.
- **Every death teaches me something specific.** A chunk that killed me is a chunk I'll recognize next time, not a random configuration I'll never see the same way twice — the game has a finite, learnable vocabulary, not an infinite firehose.

**Feelings to avoid.** A difficulty spike that reads as random rather than earned; the same chunk repeating so predictably it stops being a puzzle and becomes rote; density that outpaces what a player can physically read and react to (violating the very reaction-time budget Obstacle System's own `TOO_DENSE` check exists to enforce); an early game so thin it doesn't teach the vocabulary before the late game demands fluency in it.

**Serves the pillars.** *Pillar 2, Fair but Merciless Difficulty*: this system is the ramp itself — ramp too flat and the game never gets merciless; ramp too steep or arbitrary and it stops being fair. *Pillar 1, Instant Readability*: pacing is the lever that keeps every individual hazard readable — a perfectly clear hazard placed too close to the last one is still an unfair surprise in aggregate.

## Detailed Design

### Core Rules

1. **Data model.** A **chunk** is `{chunk_id, tier, segment_count (1-3), hazard_placements}`, where `hazard_placements` is authored in **chunk-local** coordinates: each entry is `(local_segment_index, hazard_type, footprint_pieces)` with `local_segment_index` in `[0, segment_count)`. When a chunk is placed starting at absolute segment index `base`, `hazards_for_segment(base + local_segment_index)` returns that entry's pieces, translated by `base * L` in `s` (Tube Track's `L`, `SEGMENT_LENGTH`). A chunk's hazard-type roster for MVP is Obstacle System's four illustrative types (Wall, Spike/Needle, Double Gate, Near-Ring), adopted as the real roster rather than inventing new geometry — matching systems-index's own risk mitigation ("start with a small chunk set and fix the data format early"). Near-Ring's art-bible family membership (Obstacle System Open Question 5) is not resolved here — it's routed to art-director as an open request (Open Questions), the same way this session's other GDDs have routed art-authority questions rather than deciding them unilaterally.
2. **Three difficulty tiers, unlocking over `run_time`, never shrinking the vocabulary.** `INTRO` (single hazard type, low density, the first `TIER_INTRO_DURATION` seconds), `RAMP` (multiple types, moderate density, until `TIER_RAMP_DURATION`), `FULL` (the entire chunk library, full density, thereafter). Each tier's eligible pool is a **superset** of the previous tier's — `RAMP` includes every `INTRO` chunk plus its own, `FULL` includes everything — so a pattern the player learned early never disappears from the possibility space, it just becomes one option among more.
3. **Sequencing: a seeded shuffled bag per tier, never an immediate repeat across a reshuffle.** At `run_reset`, each tier's pool is shuffled with a PRNG seeded from `run_id` (so a given `run_id` always reproduces the same sequence — deterministic and replayable, matching Obstacle System's own Core Rule 6 requirement that whatever supplies hazard layouts is responsible for its own determinism). Chunks are drawn from the current tier's bag without replacement; when a bag empties, it reshuffles, with one constraint: the reshuffled bag's first draw must not equal the just-emptied bag's last draw (no back-to-back repeat across the reshuffle boundary). This guarantees every chunk in the pool is seen before any repeats, which is what actually makes recognition possible — a naive weighted-random pick could theoretically never surface part of the library, or repeat the same chunk twice in a row. **If a tier's pool has exactly one chunk** (`N` = 1, possible only for a deliberately tiny `INTRO` pool), the no-back-to-back-repeat constraint is waived — the same, only chunk necessarily repeats every draw, which is expected and not a bug.
4. **Whole-segment alignment is forced, not authored.** Because Obstacle System's own Core Rule 1 requires every piece's raw `s`-range to fit fully inside its `home_segment`, a chunk spanning `segment_count` segments is *already* a whole number of segments by construction — there is no way to author a chunk that straddles a segment boundary even if this GDD wanted to. This resolves Tube Track's Open Question 8 (first half) as a consequence of the existing architecture, not a new decision.
5. **Negative segment indices are hazard-free.** `hazards_for_segment(index)` returns an empty array for any `index < 0` — these only exist as Tube Track's initial window-priming padding before the run's true start (`s = 0`), are never reachable during play, and get no content. Resolves Tube Track's Open Question 8 (second half).
6. **The grace zone is respected by construction, not by exception.** No chunk placed at `base = 0` may have a `local_segment_index = 0` piece with translated raw `s_start < 11` (Ball Movement Rule 5 / Obstacle System's `GRACE_ZONE_VIOLATION`). Mechanism: only the **very first** chunk draw of a run is restricted to the subset of the `INTRO` pool that is grace-zone-compliant at `base = 0`; every draw after that (including a later draw of a chunk excluded from that first pick) uses the full, unfiltered `INTRO` pool. This is a single special-cased first draw, not a standing filter — it does not remove any chunk from the tier's bag for the rest of the run, so it does not change F4's `min_gap`/`max_gap` bounds for those chunks. **The grace-compliant subset must itself contain at least 2 chunks, checked at `PatternConfig.validated()`.** This session's `/design-review` re-review found the shipped fixture's own `INTRO` pool had only one grace-compliant chunk, which means the mechanism above — correctly implemented — still degenerated into scripting the *exact same* opening chunk for every run, forever, regardless of `run_id`: a repeat player's very first read of every session stops being a puzzle after the first run, undermining Player Fantasy's "recognition is a real edge" at the one moment every run shares. An `INTRO` pool whose grace-compliant subset (at `base = 0`) has fewer than 2 members is rejected with `GRACE_POOL_TOO_SMALL`, naming the pool's actual compliant count. This is a floor on variety, not a redesign of the mechanism: the first draw still only ever selects from the compliant subset, exactly as before, and every later draw is still unrestricted.
7. **The hidden-side ban is inherited, not re-litigated.** This system must never author a piece for which Obstacle System's `hidden(hazard)` (F4, `THETA_REF`) classifies true, until Obstacle System's own Open Questions 2 and 15 resolve. This is a hard authoring constraint carried over verbatim from Obstacle System's Core Rule 8 and its newly-enforced `HIDDEN_CONTENT_FORBIDDEN` preflight check (this session's revision) — not a design choice this GDD makes or can override.
8. **Dodge-recovery spacing: a new placement rule beyond Obstacle System's reaction-time floor.** Every hazard "read" (Obstacle System's F5 definition — a single or multi-piece hazard sharing one `hazard_id`) has one or more **solution angles**, `theta_solution` — the angular center(s) of the safe gap(s) the player must occupy to pass it, defined per hazard type: for a **single-gap type** (Wall, Near-Ring), it is the angular midpoint of the raw open gap — one value. For **Double Gate** (two independent gaps), it is **two** values, one per gap — the player may take either, so a pair-check against another read must consider both. For **Spike** (a cluster of narrow exclusion arcs, not one gap — the safe zone is "anywhere outside the narrow spikes," the large majority of the circle), no `theta_solution` is defined at all: a Spike read is **exempt** from the opposing-pair classification entirely, because it imposes no single directional solution to reverse away from. Two independent reads are **opposing** if *any* pair of their respective solution angles satisfies `abs(delta_theta(theta_solution_2, theta_solution_1)) > ANGULAR_REVERSAL_THRESHOLD` (proposed default `PI/2`, a quarter-turn-or-more direction change) — the conservative, safety-first rule for a multi-gap type, since the player might commit to either gap. For every pair of opposing reads, the raw `s`-distance between them (`s_start` to `s_start`, the same reference point Formulas F2's own `s_distance` uses) must be at least `DODGE_RECOVERY_S = T_DODGE_180 * v_max` (reusing Ball Movement's own authoritative `T_DODGE_180`, not a fresh number) — strictly more than Obstacle System's own `S_MIN_SPACING` (`T_REACT * v_max`), because reaction time is enough to *read* the next hazard but not necessarily enough to *physically complete* a prior full reversal before a new one demands the opposite direction. **Within one chunk, checked at chunk-authoring time.** Every pair of reads inside a single chunk's own `hazard_placements` (Rule 1) is checked against this floor at `PatternConfig.validated()`; a chunk with an internally-opposing pair spaced below `DODGE_RECOVERY_S` is rejected with `DODGE_RECOVERY_VIOLATION`, naming the chunk and the offending pair. A chunk's own `segment_count` (1-3, Rule 1) bounds how far apart two of its own reads can ever be (up to `3*L` = 36 u at defaults), so not every author-chosen internal pairing is legal — the floor is a real constraint on internal design, not a formality. **Across chunk boundaries: the sequencer's job, not a preflight pairwise scan (Rule 9, F2c).** Because Rule 3's shuffled bag can place any two chunks from the same tier's pool adjacent to each other, and a static per-pair preflight check would require every chunk to unilaterally reserve worst-case margin against every possible neighbor — which no chunk shorter than `DODGE_RECOVERY_S` itself could ever do — this floor is guaranteed at sequencing time instead: `PatternCore` inserts hazard-free padding ahead of a chunk whose own reads would otherwise land too close to the trailing context (Rule 9). No chunk is ever rejected merely for being short, or for being safe next to some neighbors and not others; every chunk that individually passes Obstacle System's own preflight gates, this rule's within-chunk check, and Core Rule 12's angular-clustering cap is safe next to every other such chunk, because the sequencer — not the content format — carries the cross-chunk guarantee, checked against every still-relevant read that precedes it (Rule 9), not only the one placed immediately before it.
9. **Cross-chunk dodge-recovery spacing is enforced by the sequencer (F2c) against every still-relevant prior read, not just the most recently placed one.** `PatternCore` maintains a **read history**: every non-Spike read placed so far in the current run, each recorded as `(s_start, theta_solution_set)` — the read's raw `s_start` and its full set of solution angles (Rule 8) — pruned after every chunk placement to drop any entry whose `s_start` already lies more than `DODGE_RECOVERY_S` behind the run's current placement frontier (the raw `s` immediately after the most recently placed content). This pruning loses nothing: because every future read's `s_start` can only increase as the run proceeds, once an entry falls that far behind it can never again be within `DODGE_RECOVERY_S` of anything still to come. Each time Rule 3 draws the next chunk, before placing it at its natural next `base`, the sequencer checks **every** non-Spike read of that chunk (not only its first) against **every** entry still in the read history (not only the single most recently placed read): for each pair Rule 8's `opposing()` test classifies as opposing, the sequencer computes how far short of `DODGE_RECOVERY_S` that pair's *unpadded* `s`-distance would fall. If no pair falls short, the chunk is placed immediately, with zero padding. Otherwise, the sequencer inserts `padding_segments` (F2c) whole, hazard-free segments immediately before the chunk — sized to clear the *largest* shortfall among every opposing pair at once, since padding shifts the entire chunk, and every read inside it, forward by one shared amount — and only then places the chunk, at the extended `base`. After placement, every one of the chunk's own non-Spike reads is appended to the read history at its final (padded) `s_start`, and the history is pruned again as above. **This never re-draws, reorders, rejects, or substitutes the chunk Rule 3's bag selected**: the shuffled bag's own guarantees (determinism from `run_id`; `min_gap`/`max_gap` in F4, counted in *draws*, never in segments) are completely unaffected by padding, since inserting padding is not a draw. A chunk with no non-Spike reads (Spike-only) never triggers or receives padding and is placed at its natural `base`, governed only by `S_MIN_SPACING` as before (Rule 8's own Spike exemption); it also never enters the read history. **A padded segment is player-indistinguishable from an already-existing vocabulary element, not a new one.** This GDD's own fixture already contains authored hazard-free segments inside chunks (W3's `local_segment_index` = 0, REV2's `local_segment_index` = 1) — `hazards_for_segment` returns an empty array for those exactly as it does for a padding segment, and nothing in the data model or the `HazardContentProvider` contract distinguishes "an author left this segment empty on purpose" from "the sequencer inserted this segment." Padding therefore introduces no new player-facing object and needs no separate authored identity (this session's `/design-review` re-review considered and rejected requiring one, on exactly this basis); *how often* padding fires in real play remains a separate, still-open question (Open Question 11), unaffected by this point.

**Why a history, not a single `trailing_read`.** This session's `/design-review` re-review found that tracking only the single most recently placed non-Spike read, and checking only a new chunk's own first non-Spike read against it, is unsound: `opposing()` (F2) is a threshold test on angular delta, not a transitive relation, so a chunk's first read can be non-opposing against the trailing context while a *later* read in the very same chunk is genuinely opposing against that same context (or against an earlier read still within `DODGE_RECOVERY_S`) — a real `DODGE_RECOVERY_VIOLATION` that a first-read-only, most-recent-only check silently misses. **Worked counter-example** (registry defaults, `DODGE_RECOVERY_S` = 26.6, `ANGULAR_REVERSAL_THRESHOLD` = 90°): a history entry at `theta_solution` = 0, `s_start` = 0; a newly drawn chunk's first non-Spike read at `theta_solution` = 80°, `s_start` = 7.0 — not opposing against that entry (80° <= 90°), so a first-read-only check inserts zero padding. But the same chunk's *second* non-Spike read, at `theta_solution` = 170°, `s_start` = 15.0, is not opposing against the chunk's own first read either (exactly 90°, and Rule 8 uses strict `>`), yet *is* opposing against the original history entry (170° > 90°) at only 15.0 u — 11.6 u short of `DODGE_RECOVERY_S`. Checking every read of the new chunk against the full retained history catches this pair; checking only the first read against only the single most recent prior read does not.

**Why this still replaces a per-chunk margin requirement.** An earlier revision of this GDD required every non-Spike chunk to be authored at `segment_count = 3` with its reads confined to a fixed interior margin, so that any two chunks would unconditionally clear `DODGE_RECOVERY_S` regardless of adjacency. That guaranteed the same floor, but by taxing every chunk's own authoring space *permanently*: at the shipped defaults the required margin left a window narrower than a single segment, forcing every non-Spike chunk into one "empty / hazard / empty" template and making a single chunk with two genuinely opposing reads impossible to author at any tuning corner an earlier pass of this same `/design-review` actually checked. The sequencer-side mechanism guarantees the identical floor without constraining chunk authoring at all: a chunk may be any `segment_count` from 1 to 3, with placement freedom equal to a Spike chunk's today, so long as it independently satisfies Obstacle System's own preflight gates, Rule 8's within-chunk check, and Core Rule 12's angular-clustering cap — including a chunk deliberately authored with two internally-opposing reads (REV2, Fixture), which the original fixed-margin format's own math proved could never exist. Widening the check's *scope* this pass (history instead of a single trailing read; every new-chunk read instead of only its first) does not reopen that choice — it only closes a gap in how faithfully the sequencer enforces the same floor it already committed to.
10. **`T_dodge_worst` for Tube Track's F9 is `T_DODGE_180`, supplied as a configuration value, not derived per-chunk.** Because Rules 8-9 already guarantee no authored content ever demands a tighter-than-`T_DODGE_180` reversal, the single worst case Tube Track's visibility budget must protect against is exactly Ball Movement's own worst-case turn — no chunk-specific number is needed, and none is computed at runtime.
11. **Deterministic given a fixed `run_id`; no other side effects.** Given the same `run_id` (and therefore the same PRNG seed, Rule 3), Pattern & Difficulty produces bit-identical chunk sequences across runs — required for its own tests and for reproducing a specific run's content during debugging. It sends no requests to any other system; it only implements the one function Obstacle System calls.
12. **Tier pools are capped on how angularly clustered their non-Spike chunks may be, checked once at content-load time.** Rule 9's sequencer never rejects a chunk for its neighbors, which is correct for correctness but says nothing about how *often* padding actually fires in a real tier pool — three independent specialists in this session's `/design-review` re-review converged on the same finding from different angles: if a tier pool's non-Spike chunks cluster too heavily at one or two angular poles, the chunks sitting away from that cluster oppose (Rule 8) a large fraction of the pool, and the sequencer (Rule 9) then pads a large fraction of that chunk's real placements — undercutting the density this system exists to deliver, especially at `FULL` (Core Rule 2), which gets no larger an authoring canvas than `INTRO` to compensate (`segment_count` stays 1-3 at every tier). This is flagged, not merely silently observed, but — **this session's `/design-review` re-review, fourth pass, found the cap itself was miscalibrated as a hard gate and demoted it to ADVISORY** — at `PatternConfig.validated()`, for each tier's pool, `opposing_pair_fraction` (F5) is computed over every unordered pair of the pool's own non-Spike chunks; a pool whose fraction exceeds `MAX_OPPOSING_FRACTION` logs a non-blocking `EXCESSIVE_ANGULAR_CLUSTERING` advisory, naming the tier and the fraction found, but content load still succeeds. **Why ADVISORY, not BLOCKING:** a uniformly-distributed full-360°-of-solution-angles pool — exactly the angular variety game-concept.md's own Unique Hook ("a full 360° circle") implies a rich chunk library should have — already sits at `opposing_pair_fraction` ~0.50 against the shipped 0.6 threshold (only 0.10 of headroom), and as few as three genuinely-opposite-side reversal chunks in an 8-chunk pool reach 0.643 and would be rejected outright under a hard gate. A BLOCKING check whose false-positive mode is "the author used the whole circle" would have penalized angular variety rather than only lopsided pools, inverting this game's own pillar hierarchy for the sake of a pacing concern Rule 9's padding already handles without ever failing content load. This is a *pool-wide* statistic, not a per-chunk one — it does not forbid any individual chunk's angle, only an overall pool composition where opposition is pervasive rather than occasional. It is independent of, and checked in addition to, Rule 9's runtime padding mechanism and Rule 8's within-chunk check; none of the three rules substitutes for either of the others. This does not guarantee padding never fires at a pool's own runtime sequencing (Rule 9 can still pad any given adjacency) — it only flags how structurally common opposition is across the pool as a whole, for a content author's attention, not as a load-time blocker.

### States and Transitions

Pattern & Difficulty has no phase of its own; it is a pure function of `run_time` (for tier selection) and the sequential calls to `hazards_for_segment`.

| Situation | Event | Pattern & Difficulty does |
|-----------|-------|----------------------------|
| A new run begins | `run_reset(run_id)` | Reseeds the PRNG from `run_id`; reshuffles all three tiers' bags fresh; clears any in-progress chunk state; clears F2c's read history entirely (no prior reads for the run's first draw to be checked against, matching Rule 6) |
| Tube Track's window advances | `hazards_for_segment(index)` (via Obstacle System, once per new segment) | If `index < 0`: returns empty (Rule 5). Else if mid-chunk: returns the next `local_segment_index`'s pieces, translated. Else if mid-padding (Rule 9's sequencer-inserted padding ahead of the next drawn chunk, not yet exhausted): returns empty, decrements the remaining padding count. Else: determines the current tier from `run_time`, draws the next chunk from that tier's bag (Rule 3), checks every one of its non-Spike reads against every entry in the read history and inserts Rule 9's padding if any pair falls short, appends the chunk's own non-Spike reads to the history and prunes it, then returns the chunk's first segment's pieces (immediately, at zero padding, if none was needed) |
| A run's `run_time` crosses a tier threshold | none (no signal; checked lazily) | The next chunk draw uses the new tier's bag; a chunk already in progress from the old tier finishes normally, mid-chunk tier changes never truncate an authored chunk |

| Run State & Restart | in | `run_id` (from `run_reset`, for PRNG seeding), `run_time` (for tier selection) | Hard dependency; Pattern & Difficulty never sends a request back |

## Formulas

All worked examples use the registry defaults (`v_max` = 25, `T_DODGE_180` = 1.064 s, `T_REACT` = 0.25 s, `L` = 12, `T_RAMP` = 90, `OMEGA_MAX` = 3.0, `BALL_LAG_TAU` = 0.06, `SEAM_HZ_MAX` = 3.0 Hz, Tube Track registry) plus values this GDD proposes: `TIER_INTRO_DURATION` = 15 s and `ANGULAR_REVERSAL_THRESHOLD` = PI/2 (already named in Core Rule 8, formalized here), plus `MAX_OPPOSING_FRACTION` = 0.6 (Core Rule 12, F5). `TIER_RAMP_DURATION` reuses Ball Movement's `T_RAMP` (90 s) verbatim rather than an independent guess.

**F1. Difficulty tier selection (`run_time` -> tier)**

```
tier(run_time) =
    INTRO  if run_time <  TIER_INTRO_DURATION
    RAMP   if TIER_INTRO_DURATION <= run_time < TIER_RAMP_DURATION
    FULL   if run_time >= TIER_RAMP_DURATION
```

`TIER_INTRO_DURATION` defaults to 15 s, sourced from game-concept.md's own onboarding window ("teaching...within the first 10-15 seconds") — the upper end of that window, not its midpoint, because Pattern & Difficulty's INTRO tier has a coarser lesson to teach than continuous movement feel alone: a full authored chunk's readable shape, potentially seen more than once via the tier's own shuffled bag (Core Rule 3) before RAMP unlocks. It should not be shorter than the window the citation describes. `TIER_RAMP_DURATION` defaults to exactly `T_RAMP` = 90 s (Ball Movement `ball_speed_curve`, registry) rather than an independently chosen number: this deliberately ties difficulty's own escalation to complete at the same instant the speed ramp tops out at `v_max`, so a run's hardest hazard density coincides with its fastest travel speed rather than leading or lagging it — the two ramps use different shapes (a discrete 3-step tier ladder vs. a continuous speed curve) but share one endpoint by construction.

| Symbol | Type | Range | Description |
|--------|------|-------|--------------|
| `run_time` | float | `>= 0` | seconds spent in Running since `run_reset` (Run State's `run_clock`) |
| `TIER_INTRO_DURATION` | float | proposed default 15, safe range 8-20 | seconds before RAMP unlocks |
| `TIER_RAMP_DURATION` | float | proposed default 90 (= `T_RAMP`), safe range 45-240 (mirrors `t_ramp`'s own range) | seconds before FULL unlocks; must exceed `TIER_INTRO_DURATION` |
| `tier(run_time)` | enum | `{INTRO, RAMP, FULL}` | the current difficulty tier, a pure function of `run_time` |

**Output range:** a 3-valued enum, monotone non-decreasing over a run (never regresses, Core Rule 2). Requires `TIER_INTRO_DURATION < TIER_RAMP_DURATION`, checked at content-load time (a stable reject code, `TIER_ORDER_INVALID`, mirroring Obstacle System's map-validation style) — an inverted pair would mean RAMP never triggers. `TIER_INTRO_DURATION`'s safe range (8-20 s) is bounded below by Player Fantasy's "an early game so thin it doesn't teach the vocabulary" concern and above by Pillar 2's "ramp too flat" concern; `TIER_RAMP_DURATION`'s range mirrors `t_ramp`'s own 45-240 s safe range since the two are intended to move together. **Both ranges are enforced, not merely stated.** This session's `/design-review` re-review found `TIER_ORDER_INVALID` was the *only* guard on these two knobs — their own stated safe ranges were prose, not a check — so a value like `TIER_INTRO_DURATION` = 0 (or negative) passed the ordering check while silently deleting the `INTRO` tier from `run_time` = 0 onward (`INTRO` requires `run_time < TIER_INTRO_DURATION`, and `run_time >= 0` always), breaking Core Rule 6's grace-zone mechanism along with it. Each knob outside its own stated range (`TIER_INTRO_DURATION` outside `[8, 20]`, or `TIER_RAMP_DURATION` outside `[45, 240]`) is now rejected at content-load time with `TIER_DURATION_OUT_OF_RANGE`, naming the offending knob and value — checked independently of, and before, the ordering guard above.

**Example** (defaults: `TIER_INTRO_DURATION` = 15, `TIER_RAMP_DURATION` = 90): `run_time` = 8 -> INTRO. `run_time` = 15.0 -> RAMP (boundary is inclusive on the upper tier). `run_time` = 47 -> RAMP. `run_time` = 90.0 -> FULL. `run_time` = 300 -> FULL.

**F2. Dodge-recovery spacing between opposing hazard reads**

```
opposing(read_1, read_2) := abs(delta_theta(theta_solution_2, theta_solution_1)) > ANGULAR_REVERSAL_THRESHOLD    (delta_theta: Tube Track F1 / registry angle_delta)
DODGE_RECOVERY_S = T_DODGE_180 * v_max
require: s_distance(read_1, read_2) >= DODGE_RECOVERY_S   for every pair (read_1, read_2) where opposing(read_1, read_2) is true
```

`theta_solution` is the angular center of the safe gap a hazard read requires the ball to occupy (Core Rule 8). `T_DODGE_180` is reused verbatim from Ball Movement's F5a, not rederived.

| Symbol | Type | Range | Description |
|--------|------|-------|--------------|
| `theta_solution_1`, `theta_solution_2` | float | wrapped angle | the safe-gap center of two independent hazard reads |
| `ANGULAR_REVERSAL_THRESHOLD` | float | proposed default PI/2, proposed safe range `[PI/3, 2*PI/3]` (F3) | minimum angular separation between two solution angles that counts as an opposing (reversal-demanding) pair |
| `T_DODGE_180` | float | 0.94-1.4 (Ball Movement, registry) | worst-case 180-degree dodge time |
| `v_max` | float | 18-30 (Ball Movement, registry) | max ball speed |
| `DODGE_RECOVERY_S` | float | derived, `[16.92, 42.0]` across both inputs' full safe ranges | minimum raw `s`-distance required between two opposing reads |

**Output range:** `DODGE_RECOVERY_S` is a hard floor, enforced only for pairs classified `opposing`; non-opposing pairs remain governed solely by Obstacle System's `S_MIN_SPACING` (`T_REACT * v_max`). Violated -> `DODGE_RECOVERY_VIOLATION` (Core Rule 8).

**Comparison to `S_MIN_SPACING` (confirming Core Rule 8's "always the stricter floor" claim).** Both floors share the same `v_max` multiplier, so `DODGE_RECOVERY_S / S_MIN_SPACING = T_DODGE_180 / T_REACT`, independent of `v_max`. `T_REACT` = 0.25 s (fixed, not itself a tuned range in Obstacle System). At `T_DODGE_180`'s own safe-range minimum (0.94 s), the ratio is 3.76x; at its maximum (1.4 s), 5.6x. `DODGE_RECOVERY_S` is therefore always at least 3.76x `S_MIN_SPACING`, for any legal `v_max`, across the *entirety* of both knobs' registered safe ranges, not merely at shipped defaults — confirming it is never the weaker floor.

**Example** (defaults, `T_DODGE_180` = 1.064, `v_max` = 25): `DODGE_RECOVERY_S` = 26.6 u vs. `S_MIN_SPACING` = 6.25 u (ratio 4.256x).

**F2c. Sequencer padding (Core Rule 9)**

```
history                = { (s_start_i, theta_solution_set_i) : non-Spike reads placed so far, pruned to those with s_start >= placement_frontier - DODGE_RECOVERY_S }
new_reads(chunk)        = every non-Spike read of the chunk Rule 3 just drew, at its own natural (unpadded) s_start
opposing_pairs          = { (h, r) : h in history, r in new_reads(chunk), opposing(h, r) }     (Rule 8's own opposing() test, checked over every pair of h's and r's own solution angles)
shortfall(h, r)         = max(0, DODGE_RECOVERY_S - (r.s_start - h.s_start))
padding_needed_s        = max( { shortfall(h, r) : (h, r) in opposing_pairs }, default 0 )
padding_segments        = ceil(padding_needed_s / L)
```

`history` persists across chunk boundaries and across padding insertions themselves; it is re-pruned after every placement (Core Rule 9). `padding_needed_s` takes the *largest* shortfall across every opposing `(history entry, new chunk read)` pair, not only the new chunk's first read against the single most recently placed prior read, because padding shifts the entire chunk — and every read inside it — forward by one shared amount, so it must be sized to clear the worst pair at once. If the drawn chunk has no non-Spike read (Spike-only) or `history` is empty (the very start of a run, or immediately after `run_reset`), `padding_segments = 0` unconditionally — Rule 6's own first-draw restriction, not this formula, governs the very first chunk.

| Symbol | Type | Range | Description |
|--------|------|-------|--------------|
| `history` | set | size bounded by how many non-Spike reads fit within `DODGE_RECOVERY_S` of raw `s` | every still-relevant prior non-Spike read's `(s_start, theta_solution_set)`, pruned each placement |
| `padding_needed_s` | float | `>= 0`, derived | the largest shortfall across every opposing `(history entry, new chunk read)` pair |
| `padding_segments` | int | `>= 0`, derived | whole segments of hazard-free padding inserted immediately before the next chunk |

**Output range:** `padding_segments` is always a small, finite, non-negative integer for any `(T_DODGE_180, v_max, L, SEAM_HZ_MAX)` combination within their own registered *and jointly valid* safe ranges — never unbounded. **Worst-case bound, computed across every jointly-valid corner, not each parameter's own maximum taken independently:** because `DODGE_RECOVERY_S / L = T_DODGE_180 * (v_max / L)`, and Tube Track's own load-time gate requires `L >= L_min = ceil(v_max / SEAM_HZ_MAX)` (Tube Track F5) for a map to load at all, `v_max / L` can never exceed `SEAM_HZ_MAX` on any map this system will ever see — so `DODGE_RECOVERY_S / L <= T_DODGE_180_MAX * SEAM_HZ_MAX_MAX` = `1.4 * 3.0` = `4.2`, regardless of `v_max` and `L`'s individual values, giving `padding_segments <= ceil(4.2) = 5`. **This corrects a joint-corner arithmetic error from this GDD's own prior revision**, which computed a worst case of 7 using `T_DODGE_180` = 1.4, `v_max` = 30 and `L` = 6 — a combination Tube Track's own `L_INVALID` gate would reject before this system ever ran (`L_min` at `v_max` = 30, `SEAM_HZ_MAX` = 3.0 is `ceil(30/3.0)` = 10, so `L` = 6 through 9 can never legally coexist with `v_max` = 30). The true worst case, 5, is reached at e.g. `v_max` = 30, `SEAM_HZ_MAX` = 3.0, `L` = 10 (`30/10 = 3.0 = SEAM_HZ_MAX` exactly). This does not create a safety hole — 5 is still small and bounded, and it is still `>=` the shipped-defaults figure below — only the cross-parameter worst-case *number* was wrong, not the mechanism's soundness at that corner. At the shipped defaults (`DODGE_RECOVERY_S` = 26.6, `L` = 12), a single-pair worst case (a next chunk's first read landing at `s_start = 0`, immediately opposing a lone history entry at its own chunk's very last `s_start`) needs `padding_segments = ceil(26.6 / 12) = 3`, unchanged from before.

**Why this closes this session's `/design-review` finding without reopening the sequencer-vs-preflight choice itself.** The padding-at-sequencer *mechanism* (Core Rule 9, adopted in the prior revision) is unaffected — chunks are still never rejected for cross-chunk adjacency, only padded. What changed is only the *scope* `padding_needed_s` checks: every non-Spike read of the newly drawn chunk against every still-relevant prior read in `history`, instead of only the chunk's first read against only the single most recently placed prior read. See Core Rule 9 for the worked counter-example this closes (a chunk whose first read clears the trailing context at 80° but whose second read, at 170°, does not).

**Why this still guarantees Core Rule 8's floor for every chunk pairing, unconditionally, without constraining either chunk's authoring.** Each pair's shortfall is measured directly from wherever the two reads actually are — never from a fixed per-chunk margin — so padding always closes exactly the real shortfall, for every opposing pair `history` retains, not only the nearest one. A Spike-only neighbor (Rule 8's own exemption) never enters `history` and needs only `S_MIN_SPACING`, unaffected by this formula. And because padding is inserted, never a rejection, two chunks that would have been mutually incompatible under a static preflight pairwise scan are never actually incompatible here — every legal chunk (one that clears Obstacle System's own gates, Rule 8's within-chunk check, and Core Rule 12's angular-clustering cap, F5) is safe next to every other legal chunk in the same pool, which is what makes Core Rule 2's "later tiers inherit every earlier chunk unchanged" guarantee actually hold without needing to anticipate, at authoring time, which other chunks will ever share a pool with it.

**Worked example** (REV2, Fixture — a genuinely designed internal reversal, now authorable within one chunk). A 3-segment chunk with a Wall read at `s_start` = 0.5 (`theta_solution` = 0) and a Near-Ring read at `s_start` = 27.1 (`theta_solution` = PI): internal distance = `27.1 - 0.5` = 26.6 = `DODGE_RECOVERY_S` exactly, at the `>=` boundary — accepted by Rule 8's within-chunk check. This is the puzzle Core Rule 9's prior revision made impossible to author at any corner; the sequencer-side mechanism imposes no format constraint that would have prevented it.

**F3. `ANGULAR_REVERSAL_THRESHOLD` — degenerate ends and recommended safe range**

```
K              = OMEGA_MAX * BALL_LAG_TAU                              (Ball Movement F5a)
T(X, eps)      = (X - K) / OMEGA_MAX + BALL_LAG_TAU * ln(K / eps)      for eps < K <= X   (Ball Movement F5a)
cost_ratio(X)  = T(X, 0.05) / T(PI, 0.05)                              (fraction of the worst-case dodge time a reversal of angular size X actually costs)
```

Because the `ln(K/eps)` term is independent of `X`, `cost_ratio(X)` is nearly linear in `X` above `K` — a reversal's true recovery cost climbs smoothly with angular separation, not as a step function. A single binary threshold is therefore always an approximation of a continuous cost, and its placement should be chosen so the approximation's error is bounded on both sides, not picked as a round number alone.

| Symbol | Type | Range | Description |
|--------|------|-------|--------------|
| `X` | float | `[0, PI]` | angular separation between two solution angles |
| `eps` | float | fixed, 0.05 rad | the same "arrived" tolerance `T_DODGE_180` itself uses |
| `K` | float | derived, 0.18 at defaults | cap-then-lag crossover arc |
| `cost_ratio(X)` | float | `[0, 1]` | fraction of `T_DODGE_180`'s worst-case time a reversal of size `X` actually requires |

**Output range:** `cost_ratio` is bounded to `[0, 1]` by construction (`cost_ratio(PI) = 1` exactly). Because the relationship is near-linear, equal steps in `X` give near-equal steps in `cost_ratio`.

**Worked example (at defaults, `OMEGA_MAX` = 3.0, `BALL_LAG_TAU` = 0.06, `K` = 0.18, `T(PI, 0.05)` = 1.064):**

| `X` | degrees | `T(X, 0.05)` | `cost_ratio(X)` |
|---|---|---|---|
| PI/6 | 30 deg | 0.191 s | 18.0% |
| PI/3 | 60 deg | 0.366 s | 34.4% |
| **PI/2** | **90 deg** | **0.540 s** | **50.8%** |
| 2*PI/3 | 120 deg | 0.715 s | 67.2% |
| 5*PI/6 | 150 deg | 0.890 s | 83.6% |
| PI | 180 deg | 1.064 s | 100% |

**Degenerate end 1 (threshold -> 0).** At `X` = K = 0.18 rad, `cost_ratio` = 7.2%: a direction change costing barely 7% of the worst-case dodge time already gets billed the full `DODGE_RECOVERY_S` floor (~14x over-provisioned). Combined with F2's finding, a near-zero threshold classifies nearly every nonzero-separation read pair as opposing, collapsing all spacing to `DODGE_RECOVERY_S` everywhere — the weaker `S_MIN_SPACING` floor becomes unreachable, starving density.

**Degenerate end 2 (threshold -> PI).** Only near-exact antipodal pairs would be flagged; a 150-degree reversal, already costing 83.6% of the worst-case dodge time, would sail under the ~4-5.6x weaker `S_MIN_SPACING` floor (F2) — treating an almost-maximal-cost reversal as if it were cheap. The rule becomes nearly useless.

**Recommended safe range: `[PI/3, 2*PI/3]` (60-120 degrees), default PI/2.** This is not an arbitrary round-number pick: PI/3, PI/2 and 2*PI/3 are equally spaced in `X` (each PI/6 apart) and, because `cost_ratio` is near-linear, land at very nearly equally spaced cost ratios (34.4%, 50.8%, 67.2% — symmetric steps of ~16.4 points around the default). The range keeps the threshold's classification boundary within a band where the true recovery-cost ratio stays between roughly one-third and two-thirds of the worst case: never so low that a cheap correction gets billed the full floor (density starvation), never so high that a genuinely expensive near-full reversal slips under a floor sized for a much cheaper case (under-provisioned safety). This qualitative shape (near-linear cost above `K`) holds throughout `OMEGA_MAX`'s (2.75-4.0) and `BALL_LAG_TAU`'s (0-0.072) own safe ranges, not just at defaults, so the recommendation is not defaults-only — though the exact percentages shift slightly at other corners and were not separately recomputed here (flagged for the on-device spike, the same caveat Ball Movement's own F5a carries).

**Domain guard, corrected (this `/design-review` re-review found the prior revision's fix was itself mathematically wrong).** `T(X, eps)` as written above is only the *middle* of Ball Movement F5a's own three branches — F5a is branch-complete: `X <= eps` gives `0`; `eps < K <= X` gives the `(X-K)/OMEGA_MAX + BALL_LAG_TAU * ln(K/eps)` form used here; and, critically, `K <= eps` (which includes `BALL_LAG_TAU = 0`, since then `K = 0 <= eps`) gives a **third** branch, `T(X, eps) = (X - eps) / OMEGA_MAX`, where F5a needs no guard at all because the branch condition itself routes around the `ln(K/eps)` term before it is ever evaluated. This GDD's own F3 restates only the middle branch as "the" formula, which is why *its own* restated expression (not F5a) hits `0 * ln(0/0.05)` = `0 * -inf` = `NaN` at `BALL_LAG_TAU = 0` — correctly diagnosed by the prior revision, but the fix it proposed, `T(X, eps) = X / OMEGA_MAX`, is not the value the correctly-branched function actually returns there. The real value is `(X - eps) / OMEGA_MAX`, not `X / OMEGA_MAX` — at defaults (`eps` = 0.05, `OMEGA_MAX` = 3.0), `cost_ratio(PI/2)` at `BALL_LAG_TAU = 0` is `(1.5708 - 0.05) / (3.1416 - 0.05)` ≈ 49.2%, not the 50.0% the prior fix implied. **This branch is not a single removable-singularity point.** Case 3 (`K <= eps`) governs the entire sub-range `BALL_LAG_TAU <= eps / OMEGA_MAX` — roughly `0.0125` to `0.018` across `OMEGA_MAX`'s own safe range (2.75-4.0) — not just the exact value `0`. Implementation must reproduce Ball Movement F5a's full three-branch form (or delegate directly to `BallMath.T`, never restate only its middle branch) so every `BALL_LAG_TAU` in that sub-range, not only `0`, resolves through the correct branch rather than a second, inconsistent formula invented here.

**`STEER_ARC` interaction — flagged, not fully resolved.** `STEER_ARC`'s registered safe range is 2.09-PI. At the default (PI), every point on the tube is reachable (Ball Movement B8), so `ANGULAR_REVERSAL_THRESHOLD`'s classification operates over the full angular domain with no restriction. At `STEER_ARC`'s minimum (2.09 rad), Ball Movement's own notes describe an unreachable zone of size `2*PI - 2*STEER_ARC` ≈ 2.10 rad (~120.5 deg) that hazard placement must already avoid. This shrinks the arc within which two hazards' solution angles can legally sit — and if that reachable arc's own span ever fell below `2 * ANGULAR_REVERSAL_THRESHOLD`, no two legally-placed hazards could ever be classified "opposing" at all, silently voiding this rule. Deriving the exact `STEER_ARC` value at which that crossover occurs requires Ball Movement's F1 angle-wrap mapping in more detail than reviewed here — left as an Open Question, not asserted as safe by omission.

**F4. Sequencing bounds (deterministic, not probabilistic)**

```
min_gap = 2                 (draws between two consecutive occurrences of the same chunk C)
max_gap = 2*N - 1            (N = the current tier's pool size)
```

For a fair shuffle-without-replacement bag (Core Rule 3) plus the single "no back-to-back repeat across a reshuffle" constraint: within one bag of size `N`, every chunk appears exactly once, so two occurrences of the same chunk can never be fewer than `N` draws apart *except* across a reshuffle boundary, where the explicit no-repeat constraint still forbids a gap of 1 (`min_gap` = 2: at least one different chunk always falls between two draws of the same chunk). The worst case (`C` drawn first in one bag, then last in the very next bag) gives `max_gap` = `2*N - 1`.

| Symbol | Type | Range | Description |
|--------|------|-------|--------------|
| `N` | int | `>= 1` (Core Rule 3's `N`=1 waiver covers the degenerate case) | pool size for the current tier |
| `min_gap` | int | `1` at `N=1` (the only chunk repeats every draw — trivially well-defined, not undefined); `2` for `N >= 2` | fewest possible draws between two occurrences of the same chunk |
| `max_gap` | int | `1` at `N=1`; `2` (fixed, not `2N-1`) at `N=2`; `2*N - 1` for `N >= 3` | most possible draws between two occurrences of the same chunk |

**Output range:** `[2, 2*N-1]` draws for `N >= 3`, a deterministic algorithmic consequence of the shuffle-without-replacement construction plus the boundary constraint — not a probability distribution. **`N = 2` is a special case, not covered by the general formula:** with only two chunks in the pool, the no-back-to-back-repeat-across-a-reshuffle constraint forces strict alternation (A, B, A, B, ...) with zero remaining freedom — the gap between two occurrences of the same chunk is always exactly `2`, never reaching `2*N-1 = 3`. The formula's own stated lower bound (`N >= 2`) is therefore wrong at its own boundary; the correct statement is `max_gap = 2*N-1` for `N >= 3`, and `max_gap = min_gap = 2` (fixed, not a range) for `N = 2`. **Example** (INTRO tier, `N` = 4): `min_gap` = 2, `max_gap` = 7 — a player could go as long as 7 chunk-draws without seeing a specific chunk again, or as few as 2.

**On shuffle fairness.** The repeat-avoidance guarantee above is deterministic and exactly bounded, so it can be asserted directly (draw `2N` chunks from a fixed seed and check both bounds hold). What remains genuinely probabilistic is whether the shuffle algorithm itself is fair (uniformly random over all permutations, e.g. Fisher-Yates) — that needs a statistical check (e.g. a chi-square goodness-of-fit test on per-position draw frequency over many seeded runs), not a new design formula, and is picked up in Acceptance Criteria as an ADVISORY statistical check rather than assumed correct because "it's a shuffle."

**F5. Angular clustering — `opposing_pair_fraction` per tier pool (Core Rule 12)**

```
non_spike(pool)               = { chunk in pool : chunk has at least one non-Spike read }        (Spike-only chunks excluded, Rule 8's own exemption)
pairs(pool)                   = every unordered pair {c1, c2} of distinct chunks in non_spike(pool)
opposing_chunks(c1, c2)        = true if any pair of c1's and c2's own solution angles satisfies opposing() (F2)   (mirrors Rule 8's own "any pair of solution angles" rule for multi-gap types)
opposing_pair_fraction(pool)   = | { {c1,c2} in pairs(pool) : opposing_chunks(c1, c2) } | / | pairs(pool) |
```

Vacuously `0`, not rejected, when `|non_spike(pool)| < 2` (no pair exists to classify — e.g. a tier pool that is entirely Spike chunks, or has only one non-Spike chunk).

| Symbol | Type | Range | Description |
|--------|------|-------|--------------|
| `opposing_pair_fraction` | float | `[0, 1]` | fraction of a tier's own non-Spike chunk pairs F2's `opposing()` classifies as opposing |
| `MAX_OPPOSING_FRACTION` | float | proposed default 0.6, proposed safe range `[0.4, 0.8]` | preflight advisory threshold (Core Rule 12, ADVISORY); a pool above this logs `EXCESSIVE_ANGULAR_CLUSTERING` but is not rejected |

**Output range:** `[0, 1]` by construction. **Worked example** (shipped `FULL` fixture, N=8, 7 non-Spike chunks {W1, W2, W3, W4, DG1, NR1, REV2}, `C(7,2)` = 21 pairs): W1-W4 and DG1 are mutually non-opposing (`theta_solution` within `0.8` rad of each other, under the default `PI/2` threshold — 10 of the 21 pairs). `NR1` (`theta_solution` = PI) opposes all of W1-W4 and DG1 (5 pairs). `REV2` (solution angles `{0, PI}`, Rule 8's own "any pair" rule) also opposes all of W1-W4 and DG1 via its own PI-angle read (5 more pairs) and additionally opposes `NR1` (1 pair, via REV2's 0-angle read against NR1's PI — the pair is opposing because *some* combination of their angles is, even though their PI-vs-PI combination alone is not). Total opposing: `5 + 5 + 1` = `11` of `21` = `0.524`. At the shipped default `MAX_OPPOSING_FRACTION` = 0.6, this pool is **accepted** (`0.524 < 0.6`) — the mechanism catches genuinely lopsided pools without rejecting the shipped fixture, whose two most angularly distinctive chunks (`NR1`, `REV2`) are still a minority of `FULL`'s own non-Spike composition. `INTRO`'s pool (all four Wall chunks at `theta_solution` = 0) and `RAMP`'s pool (adds `DG1`, still non-opposing against the Wall cluster) both measure `0.0`, trivially accepted. *(This is illustrative of the mechanism at the default `ANGULAR_REVERSAL_THRESHOLD`; the exact fraction shifts with that threshold, same caveat F3's own worked table carries — it is not asserted to hold at every registered `ANGULAR_REVERSAL_THRESHOLD` corner.)*

**What this does and does not guarantee.** A pool passing this cap can still have Rule 9 pad any individual adjacency the shuffled bag happens to produce — this is a bound on how *structurally common* opposition is across the pool as a whole, not a bound on any single run's actual padding frequency (no formula in this GDD computes that; Open Questions tracks it as unresolved). It is deliberately a coarser, cheaper-to-reason-about signal than an exact padding-frequency simulation would be, traded off against staying a simple, deterministic preflight check rather than a statistical one.

## Edge Cases

- **If `TIER_INTRO_DURATION >= TIER_RAMP_DURATION` at content load**: rejected with `TIER_ORDER_INVALID` (F1) — an inverted or equal pair would mean `RAMP` never triggers, or triggers and instantly ends.
- **If `TIER_INTRO_DURATION` or `TIER_RAMP_DURATION` is outside its own stated safe range (`[8, 20]` / `[45, 240]`) at content load**: rejected with `TIER_DURATION_OUT_OF_RANGE` (F1) — this session's `/design-review` re-review found no guard previously enforced these ranges, only their ordering; a degenerate value like `TIER_INTRO_DURATION` = 0 passed the ordering check while silently deleting the `INTRO` tier entirely.
- **If `ANGULAR_REVERSAL_THRESHOLD` is outside its own stated safe range `[PI/3, 2*PI/3]` at content load**: rejected with `ANGULAR_THRESHOLD_OUT_OF_RANGE` — unlike `TIER_INTRO_DURATION`/`TIER_RAMP_DURATION`, this knob previously had no analogous preflight guard even though F3 names an explicit safe range and documents concrete harm at both ends (density starvation near 0, an under-provisioned floor near `PI`); this closes that gap.
- **If a tier's own pool has `opposing_pair_fraction` (F5) above `MAX_OPPOSING_FRACTION` at content load**: logs a non-blocking `EXCESSIVE_ANGULAR_CLUSTERING` advisory (Core Rule 12, ADVISORY — demoted from BLOCKING this session's `/design-review` re-review, fourth pass), naming the tier and the fraction found, but content load still succeeds — a pool whose non-Spike chunks cluster too heavily at one or two angular poles is flagged for a content author's attention before it can make the sequencer's padding (Rule 9) structurally common rather than occasional, without risking rejecting a genuinely varied, full-360° pool for the same statistic.
- **If the `INTRO` pool's grace-zone-compliant subset (chunks legal as the very first draw, Core Rule 6) has fewer than 2 members at content load**: rejected with `GRACE_POOL_TOO_SMALL` (Core Rule 6) — this session's `/design-review` re-review found the shipped fixture itself, before this fix, had only one compliant chunk, which scripted the *identical* opening chunk for every run regardless of `run_id`.
- **The sequencer's own padding computation (Rule 9, F2c) never produces a rejection.** Unlike the prior revision's per-chunk margin requirement (`EDGE_MARGIN_VIOLATION`, removed) or a static cross-chunk preflight pairwise scan, there is no chunk shape or placement padding cannot accommodate — the only observable effect of a short or awkwardly-placed chunk meeting an opposing neighbor is more inserted padding segments, bounded by F2c's own worst-case formula (AC-13). A chunk is only ever rejected for its own internal shape (Rule 8's within-chunk check, next bullet), for failing Obstacle System's own preflight gates, or for the pool-wide clustering cap above (Core Rule 12) — never for being short, and never for "being unsafe next to some *specific* neighbor," since content-population time never asks that narrower question; a chunk's own two reads, and every prior read still in F2c's history, are what's checked, not chunk-to-chunk compatibility as such.
- **If a tier's pool has exactly one chunk (`N` = 1)**: the no-back-to-back-repeat constraint (Core Rule 3) is waived for that tier — the same, only chunk repeats every draw by necessity, which is expected, not a validator failure.
- **If two reads within the *same* chunk classify as opposing (F2)**: checked identically to a cross-chunk pair — `DODGE_RECOVERY_S` applies within one chunk's own internal reads exactly as it does across a chunk boundary; there is no exemption for "the author clearly intended this."
- **Immediately after a tier transition, the newly active tier's bag may draw a chunk the just-finished tier's bag played last**: accepted, not a violation — each tier's bag is shuffled independently (Core Rule 3), and there is no cross-tier no-repeat guarantee. This is a rare, minor exception (at most two tier transitions occur per run), and the player's difficulty context has genuinely changed at that point, so an occasional near-repeat across the boundary doesn't undermine the recognition Player Fantasy asks for.
- **If `run_reset` arrives mid-sequence, with a chunk only partially delivered (some `local_segment_index`s already returned, others not)**: the in-progress chunk state is discarded along with everything else (Core Rule 11), including F2c's read history, which is cleared entirely — the new run's first `hazards_for_segment` call starts a fresh chunk draw from `INTRO`'s freshly-reshuffled bag, seeded from the new `run_id`, with no prior read to be checked against.
- **If the content library's `INTRO` pool is too small to reach `TIER_INTRO_DURATION` without repeating** (e.g. one short chunk against a 15-second window at a fast pace): not an error at the format level beyond the `GRACE_POOL_TOO_SMALL` guard above — `N` = 1's waiver (above) or a short `max_gap` (F4) just means more repetition than a larger pool would give; a content-population-time advisory check (not BLOCKING) can flag a suspiciously small `INTRO` pool for the author's attention (Acceptance Criteria).

**Fixed constants (not tuning knobs):** `segment_count`'s 1-3 range (a per-chunk authoring choice, not a global value); the chunk-library content itself (an authoring/content decision, out of this GDD's scope, same as Pattern & Difficulty being out of Obstacle System's); `GRACE_POOL_MIN_SIZE` = 2 (Core Rule 6) — a correctness floor found by this session's `/design-review` re-review, not a value with a meaningful "too high" side to tune.

**Knob interactions**
- `TIER_RAMP_DURATION` is deliberately pinned to Ball Movement's `T_RAMP` by default (F1) — changing one without the other reopens the "difficulty and speed peak at different times" question this GDD's own F1 rationale explicitly avoided.
- `ANGULAR_REVERSAL_THRESHOLD` interacts with `STEER_ARC` at `STEER_ARC`'s low end — an unresolved crossover (Formulas F3, Open Questions) that should be checked before either knob's safe range is widened.
- `ANGULAR_REVERSAL_THRESHOLD` also feeds `MAX_OPPOSING_FRACTION` (F5): raising the threshold shrinks how many pairs classify opposing at all, which mechanically lowers every pool's `opposing_pair_fraction` — the two knobs are not independent, and `MAX_OPPOSING_FRACTION`'s own safe range was chosen assuming the default `ANGULAR_REVERSAL_THRESHOLD`, not re-derived at its own range's extremes.
- `DODGE_RECOVERY_S` (derived, not itself a knob) scales with both `T_DODGE_180` (Ball Movement) and `v_max` (Ball Movement) — a change to either changes how much `s`-distance a chunk-library author must leave between opposing reads, without this GDD's own knobs changing at all.
